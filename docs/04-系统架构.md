## 1. 设计目标与原则

### 1.1 设计目标

| 目标 | 说明 |
|---|---|
| **通用** | 不绑定任何领域（中医/命理只是首个验证场景，非假设） |
| **可配置** | 处理流程、参数、组件、产出目标全靠 YAML 配置，不写代码调整 |
| **可扩展** | 通过 SPI 接口加新解析器/向量库/产出格式，不动核心 |
| **可靠** | 单文件失败不中断，断点续跑（文件×阶段粒度 + sink 幂等），优雅停机 |
| **产出灵活** | 清洗结果可落向量库，也可只产 Markdown/JSONL；不绑定任何存储 |
| **安全** | 文件上传白名单、密钥脱敏、SQL 参数化、路径穿越防护 |
| **可观测** | 结构化日志、指标埋点、进度事件，出问题能定位 |
| **可开源** | 结构清晰、文档完整、依赖合理，社区能看懂用起来 |

### 1.2 设计原则

1. **流水线优先（Pipeline First）**：核心是"把数据按阶段流过去"，不是"一个万能函数"。每个阶段职责单一、可独立测试、可跳过。
2. **接口驱动（Interface Driven）**：所有可替换组件定义为接口，默认实现可被覆盖。
3. **配置即代码（Config as Code）**：YAML 配置完整描述一次处理流程，版本化管理。
4. **产出可追溯（Traceable Output）**：每个产出的文本块都能追溯到源文件、源页码、源段落。
5. **失败隔离（Failure Isolation）**：一个文件的失败绝不影响其他文件，记日志跳过。
6. **内核纯净（Pure Core）**：`knowly-core` 不依赖任何 Web 框架，CLI 与 Web 都只是它的两个"触发器"。
7. **落库可选（Optional Persistence）**：向量化与落库解耦，默认产 Markdown，向量库是可选 sink。
8. **前向兼容（Forward Compatible）**：数据结构/配置/产出格式加字段不破坏老消费方。

## 2. 总体架构

### 2.1 分层架构

```
┌───────────────────────────────────────────────────────────┐
│   knowly-web (React + Vite, v0.1)        knowly-cli (v0.1) │
│        PC 端 Web UI                          命令行入口     │
├───────────────────────────────────────────────────────────┤
│                  knowly-api (Spring Boot, v0.1)             │
│        REST + SSE + 任务调度 + admin 认证                     │
├───────────────────────────────────────────────────────────┤
│              流水线编排引擎（Pipeline Engine）               │
│              knowly-core（纯库，不依赖 Web）                 │
│   数据模型 · SPI 接口 · 流水线引擎 · 状态存储 · 配置校验      │
├───────────────────────────────────────────────────────────┤
│  摄取层     │  清洗层     │  向量化层    │  图谱层(v0.2)    │
│  Ingest     │  Clean      │  Embed       │  Graph           │
├───────────────────────────────────────────────────────────┤
│             SPI 扩展接口层（可插拔组件）                      │
│  DocumentParser │ LayoutAnalyzer │ OcrEngine                │
│  ChunkingStrategy │ EmbeddingProvider │ ChunkSink ...      │
├───────────────────────────────────────────────────────────┤
│              基础设施（配置/日志/状态存储/错误处理/可观测）    │
├───────────────────────────────────────────────────────────┤
│  外部依赖：Tika │ Tesseract │ PostgreSQL │ Neo4j │ LLM       │
└───────────────────────────────────────────────────────────┘
```

**关键分层约束**：
- `knowly-core` 是纯库，不依赖任何 Web 框架，可被 CLI / Web / 第三方嵌入三种入口复用
- 各实现层（ingest/clean/embed）依赖 core 的接口，**模块之间不直接依赖**
- knowly-api 和 knowly-cli 是平级的两个"入口"，都依赖 core，互不依赖

### 2.2 部署模式

**前后端始终分离部署**（用户决策）：knowly-web（nginx 静态资源）+ knowly-api（Spring Boot 服务），独立发版。knowly-cli 作为独立可执行 jar。

## 3. 模块划分

知了采用 Maven 多模块，整体分为前端工程、后端聚合工程、分发与测试三大块。

### 3.1 顶层结构

```
knowly/
├── knowly-server/                   ← 后端聚合工程（Maven 父 POM）
│   ├── knowly-common/               ← 通用工具：常量/枚举/异常/DTO/工具类
│   ├── knowly-core/                 ← 内核引擎（纯库，不依赖 Web）
│   ├── knowly-ingest/               ← 摄取层实现（Tika/OCR/版面分析）
│   ├── knowly-clean/                ← 清洗层实现（编码/去重/分段）
│   ├── knowly-embed/                ← 向量化层实现（embedding + 各 sink）
│   ├── knowly-graph/                ← 图谱层实现（v0.2）
│   ├── knowly-api/                  ← Web API 层（Spring Boot，v0.1）
│   └── knowly-cli/                  ← CLI 入口（v0.1，可执行 jar）
│
├── knowly-web/                      ← 前端工程（React + Vite，v0.1）
│
├── knowly-dist/                     ← 分发包（示例配置、quickstart、样例文档）
└── docs/                            ← 八份文档
```

### 3.2 模块职责

| 模块 | 职责 | 版本 |
|---|---|---|
| **knowly-common** | 常量、枚举、全局异常、通用 DTO、工具类（HashUtils/RetryTemplate/RateLimiter/TextNormalizer/PathSanitizer/SecretMasker）。无业务逻辑 | v0.1 |
| **knowly-core** | 内核引擎：数据模型 + SPI 接口 + 流水线引擎 + 状态存储 + 配置加载校验 + 错误收集。**纯库，不依赖任何 Web 框架** | v0.1 |
| **knowly-ingest** | 摄取层实现：TikaDocumentParser、PdfDocumentParser、TesseractOcrEngine、RuleBasedLayoutAnalyzer | v0.1 |
| **knowly-clean** | 清洗层实现：DefaultTextCleaner、HashDedupStrategy、MinHashDedupStrategy、两阶段 StructureAwareChunking、SemanticChunking | v0.1 |
| **knowly-embed** | 向量化与产出实现：DashScopeEmbeddingProvider、MarkdownSink、JsonlSink、PgVectorSink（内部用包区分） | v0.1 |
| **knowly-graph** | 图谱层实现：实体/关系抽取、Neo4jGraphStore | v0.2 |
| **knowly-api** | Web API 层：Spring Boot 3 + REST + SSE + 任务调度 + admin 认证。调 knowly-core 跑清洗流水线 | v0.1 |
| **knowly-cli** | CLI 入口：main 类、命令解析、调 knowly-core 跑流水线 | v0.1 |
| **knowly-web** | 前端 SPA：React + Vite，调 knowly-api | v0.1 |

> **knowly-core 为何必须纯净**：它可被三种入口复用——CLI（v0.1）、Web API（v0.1）、第三方直接当依赖引入。若内核混进 Web 依赖，CLI 用户被迫拖一堆 Spring MVC jar，开源体验崩坏。这是架构师必须守住的边界。

### 3.3 模块依赖关系

```
knowly-cli ──→ knowly-ingest ──→ knowly-core ──→ knowly-common
           ──→ knowly-clean  ──→ knowly-core
           ──→ knowly-embed  ──→ knowly-core

knowly-api ──→ (同上 + Spring Boot Web 栈)
knowly-web ──→ knowly-api（通过 HTTP）
```

**原则**：所有实现层依赖 `knowly-core` 的接口和数据模型，**模块之间不直接依赖**。这样替换某个实现层不影响其他层。

> **演进**：v0.1 用单一 `knowly-embed` 模块，内部用包区分 embedding 生成与各 sink。v0.2 当 sink 类型增多时可拆分为 `knowly-embed` + `knowly-sink`。

## 4. 核心概念与数据流

> 本节讲系统有哪些核心概念及其关系（What），具体类定义见[后端开发文档](06-后端开发文档.md)。

### 4.1 三种核心数据载体

整个系统是一个**单向流水线**，数据在阶段间以三种载体流转：

| 载体 | 产出层 | 含义 | 是否核心资产 |
|---|---|---|---|
| **RawDocument** | 摄取层 | 一个文件解析后的产物（文本 + 元数据 + 内容哈希 + 解析状态） | 否（中间态） |
| **TextChunk** | 清洗层 | 一个知识单元（分段后的文本块 + 所属文档/章节/页码等元数据） | **是（核心资产）** |
| **EmbeddedChunk** | 向量化层 | TextChunk + embedding 向量（仅启用向量库 sink 时存在） | 否（可重算） |

**关键设计**：TextChunk 是核心资产，所有产出（Markdown/JSONL/向量库）都由它派生。embedding 与模型绑定（换模型全量重算），因此 EmbeddedChunk 不是资产，可随时重算。

### 4.2 数据流

```
原始文件        摄取层          清洗层           TextChunk[]
(PDF/DOC/  ──→  RawDocument  ─→ TextChunk[]  ──────┬──────→ MarkdownSink  → .md 文件
 图片/视频)      (文本+元数据)   (分段文本)          │
                                                     ├──(可选)──→ embed ──→ EmbeddedChunk[] ──→ 向量库 Sink
                                                     │                                  (PgVector/Qdrant/...)
                                                     └─────────→ JsonlSink → .jsonl 文件

                                                    （v0.2）TextChunk[] ──→ graph ──→ Neo4j
```

**流向关键点**：
- 是否启用 embed，取决于配置的 sink 中是否有 `requiresEmbedding()==true` 的（向量库）。全是 Markdown/JSONL 则跳过 embed，省 API 开销
- semantic chunking（F2.7）在清洗层内部消耗 embedding，但不产出 EmbeddedChunk

## 5. 流水线编排模型

> 本节讲编排模型和数据流转方式（What），Stage 接口签名和引擎实现见[后端开发文档](06-后端开发文档.md)。

### 5.1 Stage 抽象

流水线由若干 Stage 串联：Ingest → Clean → [Embed] → Sinks。每个 Stage 职责单一，接收上一阶段输出、产出本阶段输出，失败记录到 ErrorCollector 不中断。

### 5.2 PipelineEngine 职责

1. 读取 YAML 配置，实例化各 Stage 和 Sink（通过工厂+注册表）
2. 按 Stage 依赖组装流水线
3. **判断是否启用 Embed**：若所有配置的 sink 都 `requiresEmbedding()==false`，跳过向量化阶段
4. 驱动数据流转
5. 处理失败：单条失败记录到 ErrorCollector，继续
6. 持久化状态：每个 Stage 处理完更新 StateRepository
7. **发布进度事件**（观察者模式），供 CLI/Web 订阅

### 5.3 数据流转方式：流式（per document）

**采用流式处理**（按文档粒度），而非全量式。每个文档独立流转完所有阶段，内存占用恒定。

```
每个文档独立流转（streaming per document）：
  doc1: Ingest → Clean → TextChunk[] ──→ 各 Sink（含可选 Embed）
  doc2: Ingest → Clean → TextChunk[] ──→ 各 Sink（含可选 Embed）
```

**批量优化**：Embedding 阶段虽按文档流转，但调用 API 时累积到 batch_size（默认 25）再批量调用，平衡内存与 API 效率。

**并发模型**：见第 9 节"非功能性设计 - 性能"。

## 6. 关键技术决策与算法选型

> 本节讲算法思路和选型理由（Why），实现步骤见[后端开发文档](06-后端开发文档.md)。

### 6.1 两阶段分段（StructureAwareChunking）— 借鉴 Unstructured

**选型理由**：单阶段把"找结构边界"和"控大小"耦合在一个算法里，改一处伤另一处。两阶段拆开后职责分离、可独立测试、可替换。

**思路**：
- 阶段一（找边界）：遍历元素流，遇到结构边界（标题/段落/版面区域）就切，产出 pre-chunk（可能很大或很小）
- 阶段二（控大小）：太大的 pre-chunk 按 max_size 二次切分；太小的相邻 pre-chunk 合并到接近 max_size；保留 overlap

**对比单阶段的取舍**：多一层抽象（代价），但职责清晰、不同策略共享阶段二代码（收益）。不同分段策略只差阶段一的边界规则。

### 6.2 Semantic 分段（SemanticChunking）— 差异化武器

**选型理由**：竞品 Unstructured OSS 完全没有 semantic chunking（是其 SaaS 专属）。知了 v0.1 就做，是差异化优势。

**思路**：相邻文本块算 embedding 余弦相似度，相似度低于阈值处切一刀，让"语义相近的内容在一个 chunk"。

**设计为可选策略**（默认不开）：因为 semantic chunking 消耗 embedding API 调用，增加处理耗时和成本。默认用 StructureAwareChunking，用户显式配置才启用 semantic。

### 6.3 轻量版面分析（RuleBasedLayoutAnalyzer）— 借鉴 Docling/RAGFlow

**选型理由**：v0.1 不上深度学习模型（重依赖），用规则版基于 PDFBox 文本块坐标。受 Docling"版面 bbox 与文本 token 相交"启发——不靠整页 OCR 重转录，省时且准。

**思路**：
- 用 PDFBox 提取文本块坐标 + 字体大小
- 双栏检测：统计 x 坐标分布，双峰则按列分别提取
- 页眉页脚检测：每页顶部/底部固定区域、跨页重复的短文本 → 标记后去噪时移除
- 标题层级：按字体大小 + 加粗聚类
- 表格检测（简化）：密集网格线或对齐文本块 → 标记 TABLE

**v0.2 演进**：可替换为 DL 版 LayoutAnalyzer（ONNX Runtime Java 加载 DocLayNet/RT-DETR 模型）。

### 6.4 两级去重

**文件级（精确）**：内容哈希（normalize 后 SHA-256）相同 → 完全重复，保留首个。
**段落级（近似）**：MinHash + LSH，Jaccard > 阈值（默认 0.85）→ 标记但不删。

normalize 包含全角转半角、**繁简统一（中文默认开）**、去空白。繁简统一对中医/古籍资料场景必要。

> 原设计的"多版本择优"已删除。理由：可靠判定"主版本"需业务语义（权威度/时间），违反通用工具定位；段落级去重已覆盖其意图。

### 6.5 扫描版 PDF 检测

提取字符数 / 页数 < 10 → 判定扫描版 → PDF 转图片 → OCR。

### 6.6 复杂表格预期（诚实声明）

复杂表格（合并单元格/嵌套/无边框）是业界共性难题（Docling 用 TableFormer、RAGFlow 用 TSR，均不完美）。v0.1 处理能力有限：简单表格可识别，复杂表格降级为"整表作为一段文本"。v0.2 引入 TableFormer 级能力后再处理。

## 7. 配置体系策略

> 本节讲配置策略（What），完整 YAML schema 见[后端开发文档](06-后端开发文档.md)。

### 7.1 配置层级（覆盖合并）

```
全局默认 (classpath:knowly-defaults.yaml)
   ↓ 覆盖
项目配置 (--config pipeline.yaml)
   ↓ 覆盖
命令行参数 (--key value)
```

**input/output 规范**：既可在 YAML 配置，也可在命令行指定，命令行参数覆盖 YAML。

### 7.2 配置安全

- **YAML 安全**：用 SnakeYAML 的 SafeConstructor（禁任意类反序列化）
- **敏感信息**：API key 等用环境变量 `${VAR}` 引用，不硬编码
- **路径校验**：output 路径校验必须在工作目录子树内（防穿越）

### 7.3 配置校验

启动时校验配置完整性：必填项缺失、依赖关系（如开了 ocr 但没配语言、配了向量库 sink 但没配 embedding）等，**明确报错**（指出哪个字段、期望什么、实际什么、怎么改）。

## 9. 非功能性设计

> 本节是性能/安全/健壮的设计目标和约束（What），具体实现见[后端开发文档](06-后端开发文档.md)。

### 9.1 性能设计

**并发模型：有界队列 + 多阶段线程池 + 背压**

```
文件扫描 ──→ [有界队列1] ──→ Ingest线程池 ──→ [有界队列2] ──→ Clean线程池
                                                                        │
                                                                        ▼
                                                              [有界队列3]
                                                                        │
                                    ┌───────────────────────────────────┤
                                    ▼                                     ▼
                              Embed线程池                           Sink线程池(每sink一个)
                              (受RateLimiter令牌桶限流)              (PgVector/Markdown/...)
```

- **每阶段独立线程池，配置化**（如 `ingest.threads=4`）
- **阶段间有界队列**（如 `queue.capacity=100`），队列满时**阻塞上游**——这就是背压，防止快阶段压垮慢阶段
- **embedding 特殊**：受 RateLimiter（令牌桶）限流，因为 API 有 QPS 上限
- **sink 并行**：多个 sink（Markdown + PgVector）可并行写，互不阻塞

**大文件处理**：流式读取，不全量加载（GB 级文件不 OOM）。

**批量写入**：向量库 sink 支持批量 upsert（batch_size 可配），连接池复用。

### 9.2 安全设计

| 威胁 | 防护措施 |
|---|---|
| 文件上传安全 | 扩展名 + magic number 双校验白名单；大小上限（可配，默认 500MB）；zip 解压检测防炸弹 |
| 路径穿越 | PathSanitizer：`Path.normalize()` 后校验在白名单目录内 |
| 密钥泄露 | 配置加载后脱敏包装；SecretMasker 统一处理日志/异常/报告；**API key 永不出现在错误报告 JSON** |
| SQL 注入 | PgVectorSink 一律用 PreparedStatement 参数化；DDL 用受限权限账号（非 superuser） |
| 配置注入 | YAML SafeConstructor（禁任意类反序列化）；output 路径校验 |
| 不安全反序列化 | JSONL 回灌（reembed）从不可信数据读回时校验 |

### 9.3 健壮性设计

| 维度 | 设计 |
|---|---|
| 重试 | 统一 RetryTemplate（公共方法）：指数退避 + 抖动（防惊群）+ 可重试异常白名单 + 单次超时 |
| 超时分层 | 单文件解析超时 / 单页 OCR 超时 / API 调用超时 / 流水线总超时，均可配 |
| 优雅停机 | shutdown hook：停止接收新文档 → 等待进行中完成（上限 30s 超时强杀）→ flush 所有 sink → 标记状态。PipelineEngine 实现 AutoCloseable |
| 跨 sink 一致性 | 一个文档的所有 sink 写入是原子的概念：要么全成功（标记 SUCCESS），要么全回滚（各 sink 调用 deleteByDocument 补偿） |
| 资源生命周期 | 所有 Parser/OcrEngine/HTTP 客户端/DB 连接实现 AutoCloseable，try-with-resources 管理 |

## 10. 设计模式应用

> 每个模式：用在哪儿、为什么、解决什么问题。代码骨架见[后端开发文档](06-后端开发文档.md)。原则：恰当应用，不过度——能用简单方案的不引入模式。

| 模式 | 用在哪 | 为什么 |
|---|---|---|
| **工厂 + 注册表** | 组件实例化：YAML 的 `type: pgvector` 通过 SinkRegistry.create(type, config) 变成对象 | 避免硬编码 switch-case；加新组件只需写 Factory + 注册，不动核心 |
| **观察者** | 进度通知：PipelineEngine 发布 PipelineEvent，CLI/Web 各注册 listener | 内核不知道有 CLI 还是 Web；CLI 打印终端进度，Web 转 SSE 推送。线程安全（CopyOnWriteArrayList + 异步派发） |
| **责任链** | 清洗步骤串联：cleaner 一个接一个（编码→去噪→繁简→去重） | 每步独立可测，顺序可配，可增删 |
| **适配器** | 各向量库适配统一 ChunkSink 接口 | PgVector/Qdrant/Milvus API 不同，统一接口让上层无感 |
| **模板方法** | 流水线骨架固定（ingest→clean→embed→sink），各步骤可变 | 复用流程骨架，子类只填各阶段实现 |
| **策略** | ChunkingStrategy / DedupStrategy / ChunkSink | 同一问题多种算法/实现，可配置切换 |
| **建造者** | 配置对象、RetryTemplate 等多参数构造 | 避免构造函数参数爆炸，可读性好 |

## 12. 错误处理与可靠性策略

### 12.1 错误分级

| 级别 | 例子 | 处理 |
|---|---|---|
| 文件级错误 | PDF 损坏、OCR 失败 | 记录错误日志，跳过该文件，继续 |
| 阶段级错误 | 向量库连不上 | 暂停流水线，明确报错，等修复后续跑（断点续跑） |
| 配置错误 | YAML 格式错、必填缺失 | 启动时拒绝运行，明确报错 |

### 12.2 断点续跑（重点）

**状态粒度：文件 × 阶段**。StateRepository 记录每个文件在每个阶段的状态。

**断点续跑策略**：对每个文件，从"最后一个非 SUCCESS 的阶段"重新开始。

**关键陷阱：embed/sink 部分写入**。一个文档跑到一半中断，重跑会重复写部分 chunk。因此**所有 sink 必须支持幂等 upsert**：
- chunk id = `documentId#ordinal`（文件内稳定）
- documentId 由 contentHash 派生（路径变化也认作同一文档）
- 中断重跑：已写入的 chunk 被覆盖（幂等），未写入的被补齐

**为什么不在 chunk 级做细粒度续跑**：chunk 级状态会让 StateRepository 膨胀；逻辑复杂收益小（embedding 较廉价，重跑成本低）。文件级续跑 + sink 幂等已足够。

### 12.3 增量更新

扫描时对比文件 contentHash 与 StateRepository：哈希相同跳过；哈希变化或新增 → 处理，并 `sink.deleteByDocument(documentId)` 清理旧数据后重写。

## 13. Web UI 架构

> v0.1 提供 PC 端 Web UI。**定位：清洗调优工作台（不是管理平台）。**
> Web 存在的价值是可视化交互——看进度、预览分段效果、检查产出质量。**不做**知识库/文档管理/历史归档等平台功能。
> **仅本机使用**，前端 API 地址写死 `localhost`，不支持远程访问。访问保护：单 admin 账号。

### 13.1 技术栈

- 前端：**React + Vite**（独立工程 knowly-web），组件库待定。**API 地址写死 `http://localhost:8080`**，不做远程适配
- 后端：**knowly-api**（Spring Boot 3），REST + SSE

### 13.2 信息架构（工作台 + 模板 + 设置 + 登录）

```
登录页（admin 用户名+密码）
  │
  ├── 🧹 清洗工作台（主页面）
  │     - 选文件/目录（本机路径输入 + 目录浏览辅助，不上传）
  │     - 清洗参数配置（YAML 编辑 + 表单辅助）
  │     - 分段预览（调参后预览 chunk 效果——Web 核心价值）
  │     - 开始清洗（若有未完成清洗，提示"继续上次/取消/新建"）
  │     - 实时进度（SSE：阶段/进度条/成功数/失败数/日志）
  │     - 取消清洗（触发优雅停机）
  │     - 产出预览（Markdown 预览 / chunk 列表，检查清洗质量）
  │     - 完成提示（产出位置）
  │
  ├── 📋 配置模板（复用，非历史归档）
  │     - 保存当前配置为模板（YAML 文件，本地存储）
  │     - 加载模板 / 内置模板 / 删除模板
  │
  └── ⚙️ 设置
        - 修改密码
        - API Key 配置（脱敏显示）
        - 全局参数（默认 OCR 语言/分段策略/文件大小上限）
```

### 13.3 存储架构

> 知了是清洗调优工具，不存长期业务数据。SQLite 只存运行必需的结构化数据；配置模板走文件系统。

| 存储 | 存什么 | 必装 | 性质 |
|---|---|---|---|
| **SQLite**（`.knowly/knowly.db`） | users 表（admin）+ 当前运行任务状态（clean_jobs，仅当前一次，不累积历史）+ 断点续跑状态（job_files）+ 设置（app_config：API key 等） | **必装**（文件型零运维） | 运行状态 |
| **本地文件系统** | 源文件（用户本机原有）+ Markdown/JSONL 产出 + **配置模板**（`~/.knowly/templates/*.yaml`） | 必 | 文件 |
| Qdrant | 向量（可选产出目标） | 可选（配 qdrant sink 才装） | 向量库 |
| PostgreSQL + PgVector | 向量（可选产出目标） | 可选（配 pgvector sink 才装） | 向量库 |

**设计要点**：
- SQLite 只存运行必需的（admin/当前任务状态/断点/设置），**不存清洗历史**——历史是平台功能，工具不需要
- **配置模板用 YAML 文件不进数据库**——配置本来就是文件，且 CLI 也能直接用这些模板，Web 和 CLI 无缝打通
- 向量库纯可选，不配只产 Markdown/JSONL，零服务依赖

### 13.4 任务调度与断点续跑

Web 模式下清洗是长耗时任务（分钟到小时级），不能同步 HTTP。

**任务调度**：Spring `@Async`。任务状态记到 SQLite（clean_jobs 表，**只存当前运行任务，完成后状态可保留供断点续跑，但不累积为历史列表**）：
```
PENDING → RUNNING ─┬─→ SUCCESS
                   └─→ FAILED
                   └─→ CANCELED（用户取消，触发优雅停机）
```

**断点续跑**：
- 每个文件每阶段处理完，状态记到 SQLite（job_files 表，含 job_id 关联）
- 清洗中断后，用户打开 Web → 检测到有未完成清洗 → **提示"上次清洗未完成，是否继续/取消"**
- 继续 → 从断点恢复，已完成跳过；所有 sink 幂等（按 chunk id 覆盖写）保证无重复
- 取消 → 清理该任务的 job_files 状态

前端用 SSE 推送进度（订阅 PipelineEvent）。

### 13.5 admin 认证

- users 表存 admin 账号（用户名 + bcrypt 密码哈希），v0.1 仅一条记录
- 登录后发 JWT token，后续请求携带；未登录访问被拦截
- v0.1 单 admin，多用户放 v0.2（表结构已预留 user_id 字段）

## 附录 B：架构决策记录（ADR）

> 每个决策：背景 / 选择 / 理由 / 代价 / 失效场景。

| 决策 | 选择 | 理由 | 代价 | 失效场景 |
|---|---|---|---|---|
| 为何 Java 而非 Python | Java | 守一同栈；Tika/POI 是 Java 文档解析事实标准；企业级 | AI/LLM 生态弱于 Python | 图谱/semantic 等 LLM 密集功能遇 Java 瓶颈时（留 Python 后路） |
| 为何 Tika | Tika | 统一 API，1000+ 格式 | 个别格式解析质量不如专用库 | 特定格式需精细解析时加专用 Parser |
| 为何 Qdrant 默认推荐（向量库可选） | Qdrant | 专用向量库，轻量（单二进制）、低延迟；可选 sink，不配不装 | 比 PgVector 多一个服务 | 用户要少装服务时选 PgVector |
| 为何 SQLite 作核心存储 | SQLite | 文件型零运维、必装不增负担；清洗工具并发低，SQLite WAL 够用 | 不支持高并发写 | 多用户高并发时迁 PostgreSQL（接口抽象） |
| 为何业务数据不存 PostgreSQL | PostgreSQL 运行时可选 | PostgreSQL 是可选向量库，不能把必装的业务数据（admin/历史）放可选库里 | 数据分散在 SQLite（业务）+ Qdrant/PgVector（向量） | — |
| 为何两阶段分段 | 职责分离 | 找边界与控大小解耦，可独立测试替换 | 多一层抽象 | — |
| 为何 Semantic 默认不开 | 成本 | 消耗 embedding API，增加耗时 | 用户需手动启用 | — |
| 为何 Markdown 默认 sink | 零运维 + aha moment | 开源工具首次试用门槛最低；不装数据库即见产物；Git 可 diff | — | — |
| 为何 embed 与落库解耦 | 灵活 + 抗模型锁定 | embedding 与模型绑定，换模型全量重算；解耦后清洗是一次性成本 | — | — |
| 为何文件×阶段断点 + sink 幂等 | 简单可靠 | chunk 级续跑成本高收益低 | — | 极大文档单文件 embedding 成本高时（可再细化） |
| 为何 knowly-core 保持纯库 | 多入口复用 | CLI/Web/第三方嵌入都能用，不被迫拖 Web 依赖 | — | — |
| 为何 v0.1 轻量版面分析 | PDF 质量 + 免重依赖 | 学 Docling/RAGFlow，避免双栏串行；规则版免 DL 依赖 | 复杂版面识别不如 DL | 复杂版面场景（v0.2 换 DL 版） |
| 为何删除多版本择优 | 通用工具定位 | 主版本判定需业务语义，工具做不了 | — | — |
| 为何 Web UI 仅本机使用 | 工具定位 | 知了是本地清洗工具，文件在本机直接选路径不上传；远程场景复杂度不必要 | 不支持远程访问 | 未来要 SaaS 化时需重构（上传+多租户） |
| 为何前端写死 localhost | 简化 | 本机场景下浏览器连 localhost:8080 天然成立，不需要反向代理 | 部署到远程时前端连不上 | — |
| 为何单 admin 账号 | 轻量保护 | 防止 Web UI 裸奔被滥用 API key；v0.1 单人/小团队够用 | 不支持多人协作 | 多用户放 v0.2（表结构已预留） |
| 为何不要知识库概念 | 工具非平台 | 知了是一次性清洗工具（选文件→洗→拿产出），不是 RAG 平台；知识库是平台概念，套上会变重 | 清洗历史只能按时间查，不能按"库"组织 | — |
| 为何砍清洗历史改配置模板 | 工具定位 | 完整历史（记录每次清洗的统计/报告/产出）是平台思维；用户真正要的是"上次调好的参数能复用"，配置模板更轻 | 失去"看过往清洗记录"的能力 | 用户确实需要回溯运行记录时（v0.2 再加，按需） |
| 为何配置模板用 YAML 文件不进数据库 | 最轻 + CLI 打通 | 配置本来就是文件；YAML 模板 CLI 可直接用，Web 和 CLI 无缝；不建表不迁移 schema | 模板管理是文件操作，无结构化查询 | — |
| 为何用 Spring AI 作底层 | 省轮子 + 不被绑 | embedding/向量库有现成 starter，省自写 HTTP 客户端；知了 SPI 在上层，Spring AI 只是某 provider 实现细节 | Spring AI 年轻（1.0 GA 不久），API 可能变动 | Spring AI API 大改时，SPI 层隔离影响 |
