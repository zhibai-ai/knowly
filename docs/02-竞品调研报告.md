> 本报告调研了 4 个与知了最相关的竞品/参考项目，提炼知了可借鉴的设计点。
> **本报告是决策依据，排在立项背景之后、需求与设计之前**——立项的"市场缺口"判断、需求的功能取舍、设计的技术选型都引用本报告结论。
>
> **诚实声明（调研深度）**：Unstructured 为源码级深度调研（克隆仓库，结论最扎实）；Docling 基于技术报告（arXiv 论文）；RAGFlow/Dify 基于官方文档和社区资料。借鉴清单因此偏向 Unstructured，这是已知局限。我们的原则是**借鉴不是照抄**，看懂技术架构、产品思路、设计取舍即可，不做逐行级全面解读。

## 一、竞品总览与定位矩阵

| 项目 | 语言/协议 | 核心定位 | 与知了的重叠 | 知了的差异化 |
|---|---|---|---|---|
| **Unstructured.io** | Python / Apache 2.0 | "ETL for LLMs"，64+ 格式解析 | 最像知了（解析+清洗+chunking） | Java 生态；纯开源不绑 SaaS；默认 Markdown；semantic chunking（它 OSS 没有） |
| **Docling (IBM)** | Python / MIT | PDF 高质量解析 + 版面分析 | 解析+版面分析层 | Java；全流程（含向量化/图谱）；默认 Markdown |
| **RAGFlow** | Python / Apache 2.0 | DeepDoc + RAG 一体化 | 版面分析 + 流水线 | 纯造库不查库；不绑 RAG 引擎；Java |
| **Dify** | Python+Go / 开源 | Agent + RAG 平台（含 Knowledge Pipeline） | 知识库 UI / 分段配置 | 专注造库；独立工具非平台子功能 |

**核心结论**：没有一个竞品同时满足"Java + 一条龙 + 纯造库 + 多 Sink + 中文优化"五点。知了的市场空白成立。

**商业洞察**：知了的壁垒不在"技术更先进"，而在**路线选择不同**——选择了 Java、纯造库、默认 Markdown、不绑 SaaS。这些选择本身构成壁垒，因为竞品（均已押注 Python+SaaS+一体化）很难转向。

## 二、各竞品技术要点

### 2.1 Unstructured.io（源码级深度调研）

**技术选型**：
- 核心依赖：lxml/beautifulsoup4（HTML）、python-magic（类型嗅探）、spacy（POS tagging 判定 Title/Narrative）
- 按格式可选依赖：`pip install "unstructured[pdf]"`，PDF 用 pdfminer+pypdf+Tesseract
- 版面分析模型：detectron2（默认，ONNX 导出）/ yolox / chipper（自研 transformer）
- 表格识别：Table Transformer (TATR) → HTML

**最核心的设计——Element 统一抽象**：
- 所有文档格式归一化成 `List[Element]`，约 40 种类型（Title/NarrativeText/ListItem/Table/Header/Footer/Image...）
- 子类只用 `category` 类属性区分，构造签名一致，简化反序列化
- `TYPE_TO_TEXT_ELEMENT_MAP`：检测模型的细标签（Section-header/Headline → Title）归一化到核心类型，模型升级不破坏下游

**分区（Partition）SPI**：
- `FileType` enum 当声明式注册表，每个成员带 partitioner 模块名 + 依赖 + pip extras 名
- `_PartitionerLoader` 用 `importlib` 懒加载，缺依赖时明确报错提示 `pip install "unstructured[xxx]"`
- PDF 有 4 种 strategy：AUTO（默认智能选择）/FAST（纯文本）/OCR_ONLY/HI_RES（跑模型），缺依赖时优雅降级

**Chunking（重要发现）**：
- ⚠️ OSS 实际只支持 2 种：`basic`（最大化填充）和 `by_title`（遇 Title 断）。所谓 by_page/semantic/by_similarity **OSS 完全没有**（是 SaaS 付费功能）
- `Chunker` Protocol + `register_chunking_strategy()` —— 字符串名注册，第三方可扩展
- **两阶段架构**：PreChunker（按语义边界切）→ PreChunk（按大小切），basic 和 by_title 共享 90% 代码，只差阶段一的边界规则
- `ConsolidationStrategy` 枚举：合并多个元素成 chunk 时，每个 metadata 字段的降维策略（DROP/FIRST/STRING_CONCAT/LIST_UNIQUE）显式声明

### 2.2 Docling（技术报告级）

**技术选型**（来自 [Docling Technical Report, arXiv 2408.09869](https://arxiv.org/html/2408.09869v2)）：
- 版面分析模型：基于 **RT-DETR** 架构，在 **DocLayNet** 数据集训练；onnxruntime 推理，72dpi 页面图，CPU 上**亚秒级延迟**
- 表格识别：**TableFormer**（vision-transformer），能处理无边框、空单元格、单元格合并、层级表头；标准 CPU 上每表 2-6 秒
- OCR：EasyOCR（可选，216dpi），CPU 上每页可达 30 秒（较慢）
- PDF 后端：自研 docling-parse（基于 qpdf）为默认；pypdfium 为备选

**处理流水线**（线性，每页独立处理）：
```
PDF 后端（取文本 token + 坐标 + 渲染页面图）
  → 版面分析模型（检测元素 bbox + 类别）
  → TableFormer（表格结构恢复）
  → 后处理（语言检测/阅读顺序/图表匹配/元数据）
  → 组装成 DoclingDocument → JSON/Markdown
```

**关键设计点**：
- **版面分析与 PDF 文本 token 相交**（intersect）：模型检测的 bbox 与 PDF 原生文本 token 取交集，把 token 分组进段落/标题/列表等单元——**不靠 OCR 重转录，省时且准**。这是知了版面分析的核心借鉴
- 页眉页脚识别后在 Markdown 中**抑制**（suppressed），保证阅读连续性
- 跨栏段落自动拆分（5.Experiments 段落跨栏被表格打断，正确处理）
- 可扩展性：`BaseModelPipeline` 可子类化，模型链可完全自定义

### 2.3 RAGFlow DeepDoc（源码 README + 社区）

**技术选型**：
- 用 **YOLOv8** 做版面识别（DLR）和表格结构识别（TSR）
- DeepDoc 分两模块：**Vision**（OCR + 版面检测）和 **Parser**（文本/表格抽取）
- OCR 是"essential and fundamental"的基础能力

**版面组件**（10 类，覆盖大部分场景）：Text / Title / Figure / Figure caption / Table / Table caption / Header / Footer / Reference / Equation

**TSR 表格识别**：5 类标签——Column / Row / Column header / Projected row header / Spanning cell。能把表格内容重组为 LLM 易理解的句子。

**特色功能**：
- **表格自动旋转**：扫描件表格可能旋转 90/180/270°，用 OCR 置信度评估 4 个角度，选最佳朝向后重新 OCR（默认开启）
- Parser 输出：带位置信息的文本块 + 表格（裁剪图+自然语言描述）+ 图片（caption+图内文字）

**局限**（[GitHub discussion #11473](https://github.com/orgs/infiniflow/discussions/11473)）：复杂表格和流程图解析仍困难，靠启发式 + 空间对齐，非显式建模行列关系。**这是业界共性难题，知了 v0.1 同样会受限**。

### 2.4 Dify 知识库（文档级）

**技术选型**：Python+Go 后端，React 前端

**分段模式（知了 UI 可借鉴）**：
- **通用模式**：单层分段，所有分段相同设置。参数：分隔符、分段最大长度、**分段重叠长度**（相邻分段重叠字符数，防止信息在边界被切断）
- **父子模式**：双层——小**子分段**用于精准匹配检索，大**父分段**用于提供上下文响应。解决"小分段匹配准但缺上下文，大分段有上下文但匹配差"的矛盾。父分段可按**段落**或**全文**模式
- **文本预处理**（分段前）：合并连续空格/换行/制表符；删除 URL 和 email

**UI 交互（知了 Web 调优工作台借鉴，仅限可视化交互）**：
- **分段预览**：点击"预览"查看内容将如何被分段，显示有限数量分段供快速审览；调整分段规则后重新点击预览
- ⚠️ **借鉴边界**：只借鉴 Dify 的分段预览和进度可视化交互，**不借鉴其知识库/文档管理/历史等平台模式**——知了是清洗调优工具，不是平台
- 模式一旦选定不可更改（约束：避免已索引数据错乱）——**知了不借鉴此约束**，因为知了的 sink 幂等不需要它

## 三、知了可借鉴清单（经讨论确认的最终版）

> 分级说明：✅ 确定借鉴（无争议）；🟡 经讨论后确定；❌ 明确排除

### ✅ 确定借鉴

| # | 借鉴点 | 来源 | 知了落地 | 版本 |
|---|---|---|---|---|
| 1 | **版面 bbox 与文本 token 相交**（非整页 OCR） | Docling | RuleBasedLayoutAnalyzer 核心原则：PDFBox 文本块坐标分组，不靠 OCR 重转录 | v0.1 |
| 2 | **页眉页脚识别后抑制** | Docling/RAGFlow | 版面分析识别 Header/Footer 区域 → 去噪阶段移除 | v0.1 |
| 3 | **Chunker 可注册 SPI** | Unstructured | ChunkingStrategy 接口 + 注册表，字符串名实例化 | v0.1 |
| 4 | **Element/blockType 统一抽象** | Unstructured | TextChunk.blockType 枟举（HEADING/PARAGRAPH/LIST/TABLE/QUOTE/CODE） | v0.1 |
| 5 | **确定性 hash ID** | Unstructured | chunk id = `documentId#ordinal`，documentId 由 contentHash 派生 | v0.1 |
| 6 | **分段预览 UI** | Dify | Web 调优工作台的核心：调整参数后预览分段效果，这是 CLI 做不好的可视化交互 | v0.1 |
| 7 | **分段重叠（overlap）** | Dify | chunking 配置加 overlap 参数 | v0.1 |
| 8 | **表格自动旋转** | RAGFlow | 扫描件表格旋转矫正（OCR 置信度选朝向） | v0.2 |
| 9 | **表格三级切分 + 表头重复** | Unstructured | TableChunker 按行/单元格/字回退，continuation 自动带头 | v0.2 |
| 10 | **ConsolidationStrategy 元数据合并策略** | Unstructured | chunk 合并多段落时，每 metadata 字段降维策略显式声明 | v0.2 |
| 11 | **RT-DETR/DocLayNet 深度版面（可选替换规则版）** | Docling | v0.2+ 通过 SPI 替换，ONNX Runtime Java 加载模型 | v0.2+ |
| 12 | **TableFormer 表格结构恢复** | Docling | 复杂表格场景 | v0.2+ |
| 13 | **orig_elements 可溯源** | Unstructured | chunk 记录由哪些原始元素合并而来 | v0.2 |

### 🟡 经讨论后确定的决策点

| # | 借鉴点 | 讨论结论 | 版本 |
|---|---|---|---|
| 14 | **两阶段 chunking**（先按结构切粗 → 再按大小切细） | **v0.1 就拆**。职责分离比单阶段更清晰，成本不高。阶段一按结构边界切 pre-chunk，阶段二按 max_size 切 chunk，不同策略只差阶段一配置 | **v0.1** |
| 15 | **Semantic chunking**（用 embedding 余弦相似度切分） | **v0.1 就做**，作为知了的差异化武器（Unstructured OSS 完全没有）。**设计成可选策略**：默认仍用结构感知分段，用户显式配置才启用 semantic，避免默认增加 embedding 开销 | **v0.1** |

### ❌ 明确排除

| 点 | 排除理由 |
|---|---|
| **父子分段模式**（Dify） | 这是**检索端优化**（小分段匹配、大分段返回上下文），而知了是造库工具不做查询。即便知了产出父子两套分段数据，"怎么用它检索"是消费方的事，越界。且 semantic chunking（v0.1）能覆盖其大部分价值 |
| **Dify"模式选定不可改"约束** | 知了增量更新 + 幂等 sink（按 chunk id 覆盖写），改分段策略重跑即可，不需要这个约束 |
| **Unstructured FileType 的 extras 元数据** | Java SPI + ServiceLoader 已够用，不需要 Python 式的 pip extras 概念 |

## 四、知了的差异化武器（竞品都缺的）

1. **Java 生态唯一选手**——Unstructured/Docling/RAGFlow/Dify 全是 Python。Java + Tika/POI 在文档解析上有原生优势
2. **纯造库不查库**——RAGFlow/Dify 都做查询。知了专注造库，与消费方解耦
3. **默认 Markdown 产出**——竞品都强绑向量库。知了零运维，Git 可 diff
4. **Semantic chunking 原生支持**——Unstructured OSS 完全没有（SaaS 专属）。知了 v0.1 就做，即领先
5. **中文优化默认**——繁简统一、中文分段、中文实体消歧为默认，竞品都偏英文

## 五、已知风险与预期管理

**复杂表格解析是业界共性难题**（Docling 用 TableFormer、RAGFlow 用 TSR，均不完美）。知了 v0.1 的轻量版面分析**注定处理不好复杂表格**（合并单元格、嵌套表格、无边框表格）。

**预期管理**（须在需求/架构文档明确）：
- v0.1：简单表格（规则行列）可识别；复杂表格降级为"整表作为一段文本"
- v0.2：引入 TableFormer 级能力后再处理复杂表格
- 这不回避，是诚实的预期管理
