## 1. 项目概述

### 1.1 定义

知了（knowly）是开源的数据 AI 化清洗工具，把原始文档（PDF/Word/图片/视频）自动转换成 AI 可用的结构化知识（干净文本 + 向量 + 知识图谱）。详见 [立项背景](01-立项背景.md)、[竞品调研报告](02-竞品调研报告.md)。

### 1.2 核心理念

- **造库而非查库**：只负责把文档处理成知识库，不负责查询
- **配置驱动**：处理流程用配置文件定义，不写代码就能调整
- **可插拔**：LLM、embedding、向量库、图数据库、产出目标都可替换
- **产出不绑定**：清洗结果可落向量库，也可只产 Markdown/JSONL，由使用方决定
- **松耦合**：作为独立工具运行，产出标准格式，不与任何业务系统绑定

### 1.3 处理阶段与产出

| 阶段 | 产出 | 默认 Sink | 版本 |
|---|---|---|---|
| L1 摄取与清洗 | 干净文本（去噪/去重/分段） | **Markdown + JSONL（默认自动产出）** | v0.1 |
| L2 向量化 | 文本块 + embedding | PgVector（可选，不配则不落向量库） | v0.1 |
| L3 图谱化 | 实体 + 关系 | Neo4j | v0.2 |

**关键**：清洗（L1）的产出是知了的核心资产。是否落向量库、落到哪个库，由使用方在配置中选择。不配任何向量库时，默认产出 Markdown + JSONL，**零运维即可试用**。

## 2. 用户与场景

### 2.1 目标用户

- **AI 应用开发者**：要给自己的 RAG 系统准备知识库
- **企业数据团队**：要把企业文档（规章制度、技术文档等）变成 AI 可查
- **研究者**：实验不同清洗/向量化策略对检索效果的影响
- **长文档问答用户**：只要干净 Markdown，直接喂给 LLM（Cursor / Claude / 通义）

### 2.2 典型场景

**场景一：RAG 知识库构建（最常见）**
> 开发者有一批 PDF 技术文档，运行：
> `knowly run --config rag.yaml --input ./docs --output ./kb`
> 知了自动解析 PDF → 清洗分段 → 向量化 → 写入 PgVector。开发者随后在 RAG 系统里直接查这个库。

**场景二：纯清洗，不落库（零运维）**
> 研究者只想要干净文本喂给 LLM，不配任何向量库：
> `knowly run --config clean-only.yaml --input ./docs --output ./kb`
> 知了产出 Markdown + JSONL 到 `./kb`，无需安装任何数据库。可直接拖进 LLM 对话，或后续自行落库。

**场景三：知识图谱构建（进阶，v0.2）**
> 研究者想让 AI 回答跨文档的关联性问题，运行带图谱配置的流水线：知了在向量化之外，额外用 LLM 抽取实体和关系，写入 Neo4j。

**场景四：多源异构资料处理**
> 资料包含 PDF + Word + 图片（扫描件）+ 视频，知了统一摄取：Tika 解析文档、Tesseract OCR 图片、云端 ASR 处理视频，全部汇成统一文本流，再清洗向量化。

**场景五：守一国学系统的知识底座**
> 守一系统的天纪（命理）+ 人纪（中医）资料（数百 PDF + Word + 视频），用知了清洗成知识库。这是知了的第一个真实场景，但知了本身不绑定国学领域。

## 3. 功能需求

### 3.1 摄取层（Ingest）— L1

把各种格式的原始文件转成纯文本。

| 编号 | 功能 | 输入 | 输出 | 说明 | 版本 |
|---|---|---|---|---|---|
| F1.1 | PDF 解析 | .pdf 文件 | 纯文本（保留段落结构） | 自动识别文字版 vs 扫描版；扫描版转 OCR | v0.1 |
| F1.2 | Word 解析 | .doc / .docx | 纯文本 | Apache POI / Tika | v0.1 |
| F1.3 | 通用文档解析 | .ppt/.xls/.txt/.md/.html 等 | 纯文本 | Tika 统一处理 | v0.1 |
| F1.4 | 图片 OCR | .jpg/.png | 纯文本 | Tesseract，支持中英文 | v0.1 |
| F1.5 | 视频/音频 ASR | .mp4/.mp3 等 | 纯文本（带时间戳） | 调用云端 ASR API（可配置） | **v0.2** |
| F1.6 | 元数据保留 | 任意文件 | 文本 + 元数据（文件名、格式、源路径、页数等） | 每段文本可追溯来源 | v0.1 |
| F1.7 | 轻量版面分析 | PDF / 图片 | 带版面区域的文本 | 识别双栏/表格/页眉页脚/标题层级，提升清洗质量 | v0.1 |

**关键要求**：
- 格式识别自动（按扩展名 + magic number 双重判断）
- 解析失败的单个文件不中断整体流程，记录到错误日志
- 扫描版 PDF 检测：能提取的字符数 < 阈值（如每页 < 10 字符）则判定为扫描版
- **F1.7 版面分析**：受 RAGFlow DeepDoc / Docling 启发，v0.1 做轻量版（基于规则 + PDFBox 文本块坐标），不引入重型深度学习模型；v0.2 可选增强

**复杂表格预期管理（诚实声明）**：复杂表格（合并单元格、嵌套表格、无边框表格）是业界共性难题（详见[竞品调研报告](02-竞品调研报告.md)第五节）。v0.1 处理能力有限：简单表格（规则行列）可识别；复杂表格降级为"整表作为一段文本"。复杂表格结构化留待 v0.2 引入 TableFormer 级能力。

### 3.2 清洗层（Clean）— L1

把摄取的原始文本清洗成高质量文本。

| 编号 | 功能 | 说明 | 版本 |
|---|---|---|---|
| F2.1 | 编码修复 | 自动检测并统一为 UTF-8；处理 GBK/GB2312 老文件 | v0.1 |
| F2.2 | 文件名乱码修复 | 识别并修复损坏的文件名编码 | v0.1 |
| F2.3 | 去噪 | 去除页眉页脚、多余空白、重复换行、水印文字等 | v0.1 |
| F2.4 | 内容去重 | **文件级去重**（内容哈希相同）+ **段落级去重**（MinHash 相似度 > 阈值，标记不删） | v0.1 |
| F2.5 | 结构化标记 | 保留标题层级（H1/H2/H3）、段落、列表、表格等结构信息 | v0.1 |
| F2.6 | 知识点感知分段 | **两阶段分段**：阶段一按结构边界（标题/段落/版面区域）切 pre-chunk，阶段二按 max_size 切最终 chunk，保留 overlap | v0.1 |
| F2.7 | 语义分段（可选） | **Semantic chunking**：用 embedding 余弦相似度切分（相似度骤降处切一刀）。默认不启用，用户显式配置才开，避免默认增加 embedding 开销 | v0.1 |

> **说明**：原 F2.5"多版本择优"已删除。"同一内容多版本"的重复问题由 F2.4 段落级 MinHash 去重覆盖（标记但不删，由使用方/人工决定是否合并）。理由：可靠判定"主版本"需要业务语义（权威度/时间），违反通用工具定位。

**F2.4 是难点**：去重不是简单字符串比对，要处理"同一内容、不同格式/排版"的情况。需要内容哈希（normalized 后）+ 相似度（MinHash + LSH）双重判断。中文场景下 normalize **默认开启繁简统一**。

**F2.6 两阶段分段（借鉴 Unstructured）**：机械按 500 字切段会让"一个完整的方剂组成"被切成两半，破坏语义。两阶段把"找结构边界"和"控大小"解耦：阶段一只管在哪切（按标题/段落/版面区域），阶段二只管多大（按 max_size 二次切分 + 小段合并 + overlap）。不同分段策略只差阶段一的边界规则，共享阶段二。

**F2.7 Semantic chunking（差异化武器）**：竞品 Unstructured 的 OSS 完全没有 semantic chunking（是其 SaaS 专属）。知了 v0.1 就做，是差异化优势。算法：相邻文本块算 embedding 余弦相似度，相似度低于阈值处切一刀，让"语义相近的内容在一个 chunk"。

### 3.3 向量化层（Embed）— L2

把清洗后的文本块转成向量。**注意：向量化与落库解耦**——本层只产 `EmbeddedChunk`，落哪个库由 Sink 决定（见 3.7）。

| 编号 | 功能 | 说明 | 版本 |
|---|---|---|---|
| F3.1 | Embedding 生成 | 调用 embedding 模型（默认 DashScope `text-embedding-v3` / 1024 维） | v0.1 |
| F3.2 | 批处理与限流 | 大批量文本分批调用 API，控制 QPS（默认 10），支持失败重试（指数退避+抖动，最多 3 次） | v0.1 |
| F3.3 | 增量更新 | 文件变更后只重新处理变更部分（基于文件哈希） | v0.1 |

**F3.3 重要**：资料库会持续新增，不能每次全量重跑。要记录"文件→哈希→是否已处理"，只处理新增/变更。

### 3.4 图谱层（Graph）— L3（v0.2）

从文本抽取实体和关系，构建知识图谱。

| 编号 | 功能 | 说明 | 版本 |
|---|---|---|---|
| F4.1 | 实体抽取 | 用 LLM 从文本块抽取实体（人物/概念/方剂/穴位等，类型可配置） | v0.2 |
| F4.2 | 关系抽取 | 抽取实体间关系（组成/主治/相关/生克等，关系类型可配置） | v0.2 |
| F4.3 | 实体消歧 | 合并指向同一实体的不同写法（如"桂枝汤"="桂枝湯"） | v0.2 |
| F4.4 | 写入图数据库 | 默认 Neo4j | v0.2 |
| F4.5 | 社区检测（可选） | Leiden 算法把图谱聚类成社区，生成社区摘要（GraphRAG global search 用） | **v0.3** |

**F4.3 是难点**：中文领域的实体消歧比英文难（繁简、别名、简称）。需要配置领域同义词表 + embedding 相似度辅助。

**注意**：图谱层依赖具体的领域知识来定义"什么是实体、什么是关系"。知了提供框架和默认 LLM 提示词模板，但领域 schema 要可配置。

### 3.5 流水线编排（Pipeline）

把上面各层串成可配置的流水线。

| 编号 | 功能 | 说明 | 版本 |
|---|---|---|---|
| F5.1 | 配置驱动 | YAML 定义处理流程（哪些阶段、各阶段参数、产出 sink） | v0.1 |
| F5.2 | 阶段编排 | 支持线性流水线（摄取→清洗→向量化→[图谱]→[sink]） | v0.1 |
| F5.3 | 断点续跑 | 流水线中断后能从断点继续（粒度：文件 × 阶段，详见系统架构） | v0.1 |
| F5.4 | 日志与报告 | 每阶段产出处理日志、处理报告（`processing-report.json`）和错误报告（`error-report.json`） | v0.1 |
| F5.5 | 进度事件 | 流水线各阶段发布进度事件（观察者模式），供 CLI 终端展示和 Web UI SSE 推送 | v0.1 |

### 3.6 命令行接口（CLI）

> 所有操作都走 `knowly <子命令>` 形式。

| 编号 | 功能 | 命令示例 |
|---|---|---|
| F6.1 | 运行流水线 | `knowly run --config pipeline.yaml --input ./docs --output ./kb` |
| F6.2 | 单阶段运行 | `knowly ingest --input ./docs` / `knowly clean ...` / `knowly embed ...` |
| F6.3 | 查看报告 | `knowly report ./kb` |
| F6.4 | 初始化配置 | `knowly init` 生成模板配置文件 |
| F6.5 | 回灌（从 Markdown 重建向量库） | `knowly reembed --input ./kb/00-clean --sink pgvector` |

### 3.7 产出层（Sink）— 多 Sink 模式（可多选）

把清洗/向量化的产物写到不同目标。**Sink 支持多选**——用户可同时启用多个 sink（如既要 Markdown 做人读 + Git 审计，又要 PgVector 做 RAG 检索，还要 JSONL 做程序化备份）。不同 sink 消费的产物不同：Markdown/JSONL 吃 `TextChunk`，向量库吃 `EmbeddedChunk`。

| 编号 | Sink 类型 | 消费产物 | 版本 |
|---|---|---|---|
| F7.1 | Markdown（默认） | TextChunk | v0.1 |
| F7.2 | JSONL | TextChunk | v0.1 |
| F7.3 | PgVector | EmbeddedChunk | v0.1 |
| F7.4 | Qdrant（默认推荐） | EmbeddedChunk | v0.1 |
| F7.5 | Milvus | EmbeddedChunk | v0.2 |
| F7.6 | Elasticsearch | EmbeddedChunk | v0.3 |

**关键**：不配任何 sink 时，默认启用 Markdown + JSONL（零运维）。配了向量库 sink 时，自动启用向量化阶段。Web UI 中 sink 选择用**多选**（checkbox）而非单选（radio）。

## 4. 配置与扩展需求

### 4.1 配置文件示例（pipeline.yaml 设计意图）

> `stages` 用**对象**（非数组），按名称组织，便于按名跳过某阶段；`sinks` 用**数组**（可多选）。

```yaml
# 知了流水线配置示例
pipeline:
  name: "国学知识库构建"
  input: ./data/raw
  output: ./data/kb

  state:
    store: sqlite
    path: ./data/kb/.knowly/knowly.db

  stages:
    ingest:
      formats: [pdf, doc, docx, image]
      layout_analysis: light      # 轻量版面分析（v0.1）
      ocr:
        enabled: true
        languages: [chi_sim, eng]
      video:
        enabled: false             # v0.2 才支持

    clean:
      encoding: auto
      normalize:
        fullwidth_to_halfwidth: true
        traditional_to_simplified: true   # 中文场景默认开
        trim_whitespace: true
      dedup:
        file_level:
          method: hash
        paragraph_level:
          method: minhash
          threshold: 0.85
      chunking:
        strategy: structure_aware  # 两阶段：按结构切粗再按大小切细
        # strategy: semantic        # 可选：语义分段（消耗 embedding，默认不开）
        max_size: 500
        overlap: 50

    embed:                          # ⬅️ 仅当配置了向量库 sink 时才启用
      provider: dashscope
      model: text-embedding-v3
      dimensions: 1024              # 固化：影响向量库建表 DDL
      batch_size: 25
      qps_limit: 10

  # 产出目标（数组，可多选）。不配则默认 Markdown + JSONL
  sinks:
    - type: markdown
      dir: ./data/kb/00-clean
      include_chunk_markers: true
      keep_source_tree: true

    - type: jsonl
      path: ./data/kb/01-chunks/chunks.jsonl

    - type: pgvector                # 取消注释即启用向量库
      enabled: false
      host: localhost
      port: 5432
      database: knowly_kb
      user: ${PG_USER}
      password: ${PG_PASSWORD}
      table: knowledge_chunks

    # - type: qdrant               # v0.2
    #   url: http://localhost:6333
    #   collection: knowly_kb

  error_handling:
    on_file_failure: SKIP_AND_LOG
    retry:
      embedding: { max: 3, backoff: exponential, jitter: true }
```

### 4.2 可插拔点（SPI）

以下组件必须设计成接口 + 可替换实现：

| 扩展点 | 接口 | 默认实现 | 可选实现 | 版本 |
|---|---|---|---|---|
| 文档解析器 | DocumentParser | TikaDocumentParser | 自定义 | v0.1 |
| 版面分析器 | LayoutAnalyzer | RuleBasedLayoutAnalyzer（轻量规则） | DL 版（v0.2） | v0.1 |
| OCR 引擎 | OcrEngine | TesseractOcrEngine | 云端 OCR | v0.1 |
| ASR 引擎 | AsrEngine | — | 阿里云/讯飞/Whisper | v0.2 |
| 分段策略 | ChunkingStrategy | StructureAwareChunking（两阶段） | FixedSizeChunking / SemanticChunking | v0.1 |
| 去重策略 | DedupStrategy | Hash + MinHash | Embedding 相似度 | v0.1 |
| Embedding 模型 | EmbeddingProvider | DashScopeEmbeddingProvider | OpenAI / BGE 本地 | v0.1 |
| 产出目标 | ChunkSink | MarkdownSink + JsonlSink + PgVectorSink + QdrantSink | Milvus / ES | v0.1 |
| 图谱存储 | GraphStore | Neo4jGraphStore | — | v0.2 |
| LLM（图谱用） | LlmProvider | 通义千问 | DeepSeek / GLM | v0.2 |

## 5. 非功能需求（可验收指标）

### 5.1 性能

| 项 | 指标 | 验收方法 |
|---|---|---|
| 文字版 PDF 解析速度 | 单文件 < 5 秒（百页级），不含 OCR | 用样例 `tea-single-column.pdf` 计时 |
| 扫描版 PDF OCR 速度 | 单页 < 3 秒（含渲染图片 + Tesseract） | 用样例 `tea-scanned.pdf` 计时 |
| Embedding 限流 | 可配置 QPS，默认 10 QPS，令牌桶算法 | 压测验证不超 QPS |
| 大批量处理 | 1000 文件流水线 < 1 小时（含 embedding + OCR） | 用样例批量跑计时 |
| 单文件内存 | < 1GB | JVM 监控 |
| 并发模型 | 有界队列 + 多阶段线程池 + 背压（队列满阻塞上游） | 架构约束，代码评审验证 |
| 大文件处理 | GB 级文件不 OOM（流式读取，不全量加载） | 用大 PDF 验证不 OOM |

### 5.2 可靠性

| 项 | 指标 | 验收方法 |
|---|---|---|
| 单文件失败不中断 | 任何单文件失败，记录错误并跳过 | 用样例 `corrupted-broken.pdf` 验证流程继续 |
| 断点续跑 | 中断可恢复，文件 × 阶段粒度，sink 幂等 | 中断后重启，无重复数据 |
| 重试策略 | 统一 RetryTemplate：指数退避 + 抖动，最多 3 次 | 配置可改，验证生效 |
| 超时分层 | 单文件解析超时 / 单页 OCR 超时 / API 调用超时 / 流水线总超时，均可配 | 故意制造慢文件验证超时触发 |
| 可复现 | 相同输入 + 相同配置，产出相同结果（embedding 除外） | 重跑对比 |
| Sink 幂等 | 所有 sink 按 chunk/document id 主键幂等 | 中断重跑验证无重复 |
| 优雅停机 | 收到 SIGTERM 后停止接收新文档、等待进行中完成、flush sink、标记状态，上限 30 秒 | kill 验证状态正确 |
| 跨 sink 一致性 | 一个文档的多个 sink 写入要么全成功要么全回滚（补偿事务） | 中断在多 sink 写入中间验证 |

### 5.3 安全性

| 项 | 指标 | 验收方法 |
|---|---|---|
| 文件读取白名单 | 扩展名 + magic number 双校验（本机读取，非上传） | 用伪装文件验证被拒 |
| 文件大小上限 | 可配，默认单文件 500MB | 超大文件验证被拒 |
| 路径穿越防护 | PathSanitizer：`Path.normalize()` 后校验（本机场景仍需防恶意路径输入） | 构造 `../../etc/passwd` 验证被拒 |
| admin 登录保护 | Web UI 必须登录才能访问，密码哈希存储（bcrypt） | 未登录访问被拦截 |
| 密钥脱敏 | API key 永不出现在日志/报告/异常/UI；SecretMasker 统一处理 | grep 日志验证无明文 key |
| SQL 注入防护 | 所有数据库操作用 PreparedStatement 参数化 | 代码评审 + 注入测试 |
| YAML 安全 | 用 SafeConstructor（禁任意类反序列化） | 构造恶意 YAML 验证不执行 |
| 最小权限 | DDL 执行用受限权限账号（非 superuser） | 验证账号权限 |

## 6. Web UI 功能需求（v0.1）

> v0.1 提供 PC 端 Web UI。**定位：清洗调优工作台（不是管理平台）。**
> Web 存在的价值是可视化交互——让"看进度、预览分段效果、检查产出质量"这几件 CLI 做不好的事体验更好。
> **不做**知识库管理、文档管理、清洗历史归档、多用户协作等平台功能。
> 用户心智：选文件 → 调参数 → 预览效果 → 满意了开洗 → 看进度 → 拿产出 → 完事。
> 技术前提：**仅本机使用**，前端 API 地址写死 `localhost`，不支持远程访问。
> 访问保护：**单 admin 账号**登录（用户名+密码），防止 Web UI 裸奔被滥用 API key。

### 6.1 清洗工作台（主页面）

| 编号 | 功能 | 说明 |
|---|---|---|
| W1.1 | 选择文件/目录 | 输入本机文件或目录路径（支持手输 + 目录浏览辅助）；不上传文件 |
| W1.2 | 清洗参数配置 | YAML 编辑器（语法高亮）+ 表单辅助：分段策略/sink 选择（多选：Markdown/JSONL/Qdrant/PgVector）/OCR 语言等 |

## 7. 版本规划

### v0.1.0（MVP）— 当前目标

**目标**：跑通"PDF/Word → 清洗（含版面分析）→ 向量化 → Sink"全流程 + **完整 Web UI**，用守一的天纪资料验证。

包含：
- ✅ 摄取层：PDF / Word / 通用文档（Tika）+ 图片 OCR（Tesseract）+ 轻量版面分析
- ✅ 清洗层：编码修复 / 去噪 / 去重（hash+minhash）/ 两阶段分段 / semantic 分段（可选）
- ✅ 向量化层：DashScope `text-embedding-v3` / 1024 维
- ✅ 产出层：Markdown + JSONL + PgVector（多 Sink，可多选）
- ✅ 流水线：YAML 配置 + CLI + 进度事件
- ✅ 断点续跑（文件 × 阶段粒度）+ 错误日志 + 报告
- ✅ **Web 调优工作台（PC 端，本机使用）**：清洗工作台（选文件/调参/分段预览/进度/产出预览）/ 配置模板 / 设置 / 登录（admin 单账号）
- ❌ 视频 ASR（放 v0.2）
- ❌ 图谱层（v0.2）

**验收场景**：用守一天纪八字命理资料（PDF + Word）跑一遍，产出 PgVector 向量库 + Markdown，在守一系统里能做 RAG 问答；且全程可通过 Web UI 操作。

**v0.1 必须为 v0.2 预留的扩展点**（不实现功能，但接口和数据结构要预留，否则 v0.2 要改已稳定的 core）：

| 预留项 | v0.1 做什么 | 支撑 v0.2 哪个功能 |
|---|---|---|
| `LlmProvider` SPI 接口 | 定义接口，不实现 | 图谱层（实体/关系抽取用 LLM） |
| `EntityExtractor` / `RelationExtractor` / `GraphStore` SPI 接口 | 定义接口，不实现 | 图谱层 |
| `AsrEngine` SPI 接口 | 定义接口，不实现 | 视频 ASR |
| `LayoutAnalyzer` SPI 接口 | 定义接口 + 规则版默认实现 | v0.2 DL 版版面分析（替换实现即可） |
| `ChunkSink` SPI 通用抽象 | 接口设计不写死 PgVector | Qdrant / Milvus（加实现即可） |
| `TextChunk.blockType` 含 `TABLE` 类型 | 枚举预留 | 表格结构化（TableFormer） |
| `RawDocument.metadata.extra` Map | 字段预留 | 视频 ASR 时间戳存储 |
| `StateRepository` 接口可扩展 | 设计支持后续加目录监听 | 增量更新完善 |

### v0.2.0

**新增功能**：
- 图谱层：实体抽取 / 关系抽取 / Neo4j 写入
- 更多向量库：Milvus（Qdrant 和 PgVector 已在 v0.1 支持）

- 多用户、权限、协作

## 附录 B：JSONL 产出格式规范

每行一个 JSON 对象，字段与数据模型对齐：

```json
{
  "id": "doc-abc123#128",
  "documentId": "doc-abc123",
  "sourcePath": "/data/raw/针灸学.docx",
  "fileName": "针灸学.docx",
  "format": "docx",
  "text": "肺手太阴之脉，起于中焦，下络大肠……",
  "ordinal": 128,
  "metadata": {
    "sectionTitle": "手太阴肺经/循行路线",
    "sectionLevel": 2,
    "startPage": 45,
    "charCount": 487,
    "blockType": "PARAGRAPH",
    "tags": []
  }
}
```

**id 规则**：`{documentId}#{ordinal}`，文件内稳定，保证 sink 幂等。
**documentId 规则**：由内容哈希派生（路径变化也认作同一文档，解决文件移动问题）。
**前向兼容**：metadata 字段可扩展（新增字段不破坏老消费方）。
