## 一、命名规范（通用原则）

命名是代码可读性的第一关。原则：**见名知义、风格统一、不缩写（除领域通用缩写如 URL/HTTP/ID）。**

| 对象 | 通用原则 | 具体规则见各自规范 |
|---|---|---|
| 变量/方法 | 见名知义，避免 `data`/`temp`/`info` 这类无意义名字 | 后端 camelCase / 前端 camelCase |
| 布尔值 | 用 `is`/`has`/`should`/`can` 前缀（如 `isEnabled`/`hasContent`） | 前后端通用 |
| 常量 | UPPER_SNAKE_CASE | 前后端通用 |
| 避免缩写 | 除领域通用缩写（URL/HTTP/ID/DTO），不缩写（用 `document` 不用 `doc`） | 前后端通用 |
| 避免否定 | 布尔用正向（`isEnabled` 不用 `isNotDisabled`） | 前后端通用 |

## 二、注释规范（通用原则）

注释维护成本高，无意义注释是噪声。原则：**注释 Why（为什么这么做），不注释 What（代码做了什么）。**

| 场景 | 规则 | 理由 |
|---|---|---|
| public API / SPI 接口 | **必须文档注释**，写清契约（参数含义、返回值、异常、幂等性、副作用） | 接口是契约，没文档等于没法扩展。后端 Javadoc / 前端 JSDoc |
| 复杂算法 | 必须注释 Why（为什么这么实现，思路是什么） | 算法的意图代码读不出来 |
| 业务规则 | 涉及业务判断的逻辑必须注释依据（如"繁简统一默认开，因中医古籍多繁体"） | 业务决策的来龙去脉 |
| 一般代码 | 能从代码读出的不写注释 | 减少噪声 |
| TODO/FIXME | 必须带原因（`// TODO: xxx，因为 yyy`） | 否则永远没人做 |
| 禁止 | 注释掉的代码（用 Git 管理历史，不要留注释代码） | 噪声 |

## 三、Git 规范

### 3.1 分支模型（极简）

```
main          ← 稳定可发版，受保护，不直接推
feature/xxx   ← 功能开发
fix/xxx       ← 缺陷修复
```

- v0.1 不需要 git-flow 的 develop/release/hotfix 分支，那是过度工程
- 所有改动从 main 切分支，完成后合并回 main

### 3.2 提交信息（Conventional Commits）

```
<type>: <简要描述>

<可选正文：改了什么、为什么>
```

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档变更 |
| `refactor` | 重构（不改功能） |
| `test` | 测试相关 |
| `chore` | 构建/工具/依赖等杂项 |
| `perf` | 性能优化 |

示例：
```
feat: 实现两阶段 StructureAwareChunking

阶段一按结构边界切 pre-chunk，阶段二按 max_size 切 chunk。
借鉴 Unstructured 的两阶段架构，职责分离便于独立测试。
```

### 3.3 提交粒度

- **一个提交做一件事**，不混杂多个无关改动
- 提交信息描述"为什么改"，diff 本身展示"改了什么"
- 能 revert 单个提交而不影响其他功能

### 3.4 合并

- v0.1 单人开发：本地审核通过后，自己上传自己 merge
- 合并方式：feature 分支用 squash merge（保持 main 历史整洁）

## 四、代码评审（CR）

### 4.1 流程（v0.1 单人开发）

v0.1 主要是开发者（AI）+ 审核者（用户本地审核），不强制二人 CR。但遵循以下自我审核纪律：

| 项 | 规则 |
|---|---|
| 提交前自审 | 按 CR 关注点自检一遍（见下），不要写完就交 |
| 架构核心改动 | knowly-core / SPI 接口 / 数据模型的改动，必须在提交描述里说明影响范围 |
| 能工具拦截的不人工挑 | 格式问题交给 spotless/Prettier，不人工纠格式 |

### 4.2 CR 关注点（优先级从高到低）

1. **正确性**：逻辑对不对？边界处理了吗？
2. **安全**：有注入/泄露/越权风险吗？
3. **性能**：有明显的性能问题吗（循环内创建对象、不必要的全量加载）？
4. **规范**：符合本文档规范吗？
5. **可读性**：别人能看懂吗？

## 五、测试规范（通用原则）

| 项 | 规则 | 理由 |
|---|---|---|
| 测试结构 | AAA 模式：Arrange（准备）/ Act（执行）/ Assert（断言） | 结构清晰 |
| 测试命名 | `should_xxx_when_xxx`（如 `should_dedup_when_content_hash_same`） | 看名字就知道测什么场景 |
| 边界必测 | 空输入、超大输入、损坏输入、null/undefined | 边界是 bug 高发区 |
| 测试独立 | 不依赖执行顺序，不依赖外部状态 | 可任意顺序运行 |
| 一个测试一个断言重点 | 不在一个测试里塞多个不相关的断言 | 失败时定位清晰 |
| 不为覆盖率凑数 | 测有意义的行为，不为达到覆盖率写无意义测试 | 覆盖率是手段不是目的 |

具体测试框架（后端 JUnit 5 / 前端 Vitest）见各自规范和[测试文档](08-测试文档.md)。

## 六、安全编码（跨端铁律）

> 前后端各自的安全细则见各自规范，这里定义跨端的铁律。

| 铁律 | 说明 |
|---|---|
| 密钥不进代码 | API key、密码、token 等一律用环境变量，不硬编码、不进 Git |
| 密钥不进日志 | 任何日志/报告/异常信息中不得出现明文密钥 |
| 密钥不进前端 | 前端代码是公开的，敏感信息（后端 API key 等）绝不进前端代码 |
| 不信任外部输入 | 所有外部输入（文件、用户输入、API 参数）必须校验后再用 |
| 最小权限 | 按需授权，数据库账号/文件权限/网络访问都取最小 |
| 依赖安全 | 定期检查依赖漏洞（后端 OWASP/maven，前端 npm audit） |

## 七、文档与代码同步

| 项 | 规则 |
|---|---|
| 接口变更同步文档 | SPI 接口/数据模型/产出格式变更，必须同步更新后端开发文档和接口对接文档 |
| README 与实际一致 | README 的 quickstart 必须能跑通，不能跑的及时更新 |
| 变更可追溯 | 重要变更在提交信息或 PR 描述里记录"改了什么、为什么、影响什么" |
