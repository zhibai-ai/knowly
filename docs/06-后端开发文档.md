## 1. 开发环境搭建

> 开发前必须完成的环境配置。**按需安装**——开发不同模块需要的依赖不同，不必一次全装。
> 生产环境部署见[部署文档](07-部署文档.md)，两者不重复（开发环境给开发者本地用，部署文档给生产环境用）。

### 1.1 必装（所有开发者）

| 工具 | 版本要求 | 用途 | 验证 |
|---|---|---|---|
| JDK | 17+ | Java 运行时 | `java -version` 显示 17 以上 |
| Maven | 3.8+ | 构建工具 | `mvn -version` |
| Git | 任意 | 版本控制 | `git --version` |
| IntelliJ IDEA | Community 即可（推荐） | IDE | — |

**IDEA 推荐插件**：
- Lombok（如使用）
- Checkstyle（对接项目的 checkstyle.xml）
- Spotless（对接格式化）

### 1.2 按需安装（取决于开发哪块）

| 开发模块 | 需要装什么 | 理由 |
|---|---|---|
| **摄取层**（knowly-ingest，OCR 相关） | Tesseract 5.x + 中文语言包（`tesseract-ocr-chi-sim`）+ 中文字体（fonts-noto-cjk） | 扫描版 PDF / 图片 OCR 需要 |
| **向量化层**（knowly-embed，PgVectorSink） | PostgreSQL 15+ + PgVector 扩展 | 向量库 sink 测试需要真实数据库 |
| **embedding / semantic chunking** | DashScope API Key（环境变量 `DASHSCOPE_API_KEY`） | 调用 embedding API 需要密钥 |
| **图谱层**（v0.2） | Neo4j 5.x | 图数据库 |

> **最小开发集**：如果只开发清洗层（knowly-clean）或核心（knowly-core），只需必装项（JDK + Maven），不需要任何外部服务。先用最小集跑通，再按需扩展。

### 1.3 本地跑通（Hello World）

clone 后第一步：确认项目能构建、能跑通基础功能。

```bash
# 1. 克隆
git clone <repo-url> knowly
cd knowly/knowly-server

# 2. 构建（首次会下载依赖，较慢）
mvn clean install -DskipTests

# 3. 生成测试样例（用于验证）
cd ../knowly-dist/examples/samples
pip install python-docx Pillow PyMuPDF fonttools
python generate_samples.py

# 4. 用 clean-only 配置跑一遍（不装数据库也能验证摄取+清洗+Markdown 产出）
cd ../../../knowly-server
java -jar knowly-cli/target/knowly-cli.jar run \
  --config knowly-dist/examples/clean-only.yaml \
  --input ../knowly-dist/examples/samples \
  --output ./test-output

# 5. 检查产出
ls ./test-output/00-clean/    # 应有 Markdown 文件
```

**跑通标志**：`test-output/00-clean/` 下出现清洗后的 Markdown 文件，且 `test-output/02-reports/processing-report.json` 显示处理成功。

### 1.4 开发 PgVectorSink（需要 PostgreSQL + PgVector）

**本机环境（已就绪）**：知了使用独立的 PostgreSQL 容器（与 wenshu 的 PG 隔离，互不干扰）。

```bash
# 知了专用 PostgreSQL+PgVector 容器（已创建）
# 镜像: pgvector/pgvector:pg16（含 PgVector 0.8.5）
# 容器名: knowly-postgres
# 端口: 5433（5432 被 wenshu 占用，故用 5433）
# 数据库: knowly / 用户: knowly / 密码: knowly_dev

# 启动（如已停止）
docker start knowly-postgres

# 验证
python3 -c "import psycopg2; c=psycopg2.connect(host='localhost',port=5433,user='knowly',password='knowly_dev',dbname='knowly'); print('✓ 连接成功')"

# 启用 PgVector 扩展（首次需要）
psql -h localhost -p 5433 -U knowly -d knowly -c "CREATE EXTENSION IF NOT EXISTS vector;"
# 或用 python:
python3 -c "import psycopg2; c=psycopg2.connect(host='localhost',port=5433,user='knowly',password='knowly_dev',dbname='knowly'); c.cursor().execute('CREATE EXTENSION IF NOT EXISTS vector'); c.commit(); print('✓ PgVector 已启用')"
```

**配置环境变量**（PgVectorSink 连接用）：
```bash
export PG_HOST=localhost
export PG_PORT=5433        # 注意是 5433 不是默认 5432
export PG_USER=knowly
export PG_PASSWORD=knowly_dev
export PG_DATABASE=knowly
```

**执行建表 DDL**：见本文档第 7.3 节（方案 B：PgVector）。

> **注意端口**：wenshu 的 PostgreSQL 占用 5432，知了用 5433。配置文件里的 `port: 5432` 是标准示例，实际连接用环境变量 `PG_PORT=5433` 覆盖。配置示例（pipeline.yaml）：
>
> ```yaml
> sinks:
>   - type: pgvector
>     host: ${PG_HOST:localhost}
>     port: ${PG_PORT:5433}
>     user: ${PG_USER:knowly}
>     password: ${PG_PASSWORD}        # 从环境变量读，绝不硬编码
>     table: knowledge_chunks
> ```

### 1.5 开发摄取层 OCR（需要 Tesseract 时）

```bash
# 安装 Tesseract + 中文
sudo apt install tesseract-ocr tesseract-ocr-chi-sim

# 安装中文字体（FPDF 渲染中文需要）
sudo apt install fonts-noto-cjk

# 验证
tesseract --version
tesseract --list-langs    # 应含 chi_sim
```

### 1.6 配置 DashScope API Key

```bash
# 申请：https://dashscope.aliyun.com/
export DASHSCOPE_API_KEY=sk-xxxxx

# 验证（在 embedding 测试里会用到）
echo $DASHSCOPE_API_KEY
```

> ⚠️ 密钥不进代码、不进 Git。只在环境变量里。提交前确认密钥未误提交（开发规范的跨端安全铁律）。

### 1.7 常见问题

| 问题 | 原因 | 解决 |
|---|---|---|
| `mvn install` 失败：找不到依赖 | 网络问题或 Maven 镜像未配 | 配置阿里云 Maven 镜像（settings.xml） |
| OCR 报错：找不到 Tesseract | Tesseract 不在 PATH | `which tesseract` 确认，或重装 |
| 中文渲染乱码（生成样例时） | 缺中文字体 | `sudo apt install fonts-noto-cjk` |
| PgVectorSink 报错：extension vector 不存在 | PgVector 扩展未装 | 见 1.4 节安装 PgVector |
| embedding 报错：401 Unauthorized | API key 未配或无效 | 检查 `DASHSCOPE_API_KEY` 环境变量 |
| 扫描版 PDF 检测不到 | 字符数阈值偏高 | 检查 `min_chars_per_page` 配置 |

## 3. 核心数据模型

> 定义在 knowly-core，所有阶段共享。使用 Java record（不可变、并发安全）。

### 3.1 RawDocument（原始文档）

摄取层产出，一个文件解析后的产物。

```java
public record RawDocument(
    String id,                    // documentId，由 contentHash 派生（路径变化也稳定）
    String sourcePath,            // 源文件路径
    String fileName,              // 文件名（已修复乱码）
    String format,                // 格式（pdf/docx/image/...）
    String content,               // 提取的纯文本（含版面结构标记）
    DocumentMetadata metadata,
    String contentHash,           // 内容哈希（normalize 后 SHA-256）
    ParseStatus status            // SUCCESS/PARTIAL/FAILED
) {}

public record DocumentMetadata(
    long fileSize,
    int pageCount,                // PDF 页数
    String author,
    LocalDateTime createdTime,
    String parserUsed,            // 用了哪个解析器
    Map<String, String> extra     // 格式特定元数据（如视频 ASR 时间戳，v0.2 预留）
) {}
```

### 3.2 TextChunk（文本块）— 核心资产

清洗层产出，一个知识单元。**这是知了最核心的产出物**。

```java
public record TextChunk(
    String id,                    // documentId + "#" + ordinal（文件内稳定，保证 sink 幂等）
    String documentId,            // 所属文档ID（追溯源）
    String sourcePath,            // 源文件路径（冗余，方便追溯）
    String text,                  // 块文本内容
    int ordinal,                  // 在文档中的顺序
    ChunkMetadata metadata
) {}

public record ChunkMetadata(
    String sectionTitle,          // 所属章节标题
    int sectionLevel,             // 标题层级（1=H1, 2=H2...）
    int startPage,                // 起始页码（PDF）
    int charCount,                // 字符数
    BlockType blockType,          // 块类型枚举：HEADING/PARAGRAPH/LIST/TABLE/QUOTE/CODE
    List<String> tags,            // 自动打的标签
    List<String> origElementIds   // 可溯源：本 chunk 由哪些原始元素合并而来（v0.1 预留字段，v0.2 启用）
) {}
```

**id 生成规则**：`{documentId}#{ordinal}`，文件内稳定，保证 sink 幂等。
**documentId 规则**：由 contentHash 派生（`"doc-" + contentHash.substring(0, 12)`），路径变化也认作同一文档。

### 3.3 EmbeddedChunk（向量化后的块）

向量化层产出。仅当配置了向量库 sink 时才存在。

```java
public record EmbeddedChunk(
    String id,                    // 与 TextChunk.id 一致
    String text,                  // 文本（冗余存向量库，便于检索展示）
    float[] embedding,            // 向量（维度 1024，text-embedding-v3）
    String documentId,
    Map<String, Object> metadata  // 完整元数据
) {}
```

### 3.4 Entity / Relation（图谱，v0.2）

```java
public record Entity(
    String id,
    String name,                  // 实体名（规范化后）
    String type,                  // 类型（方剂/穴位/概念...）
    String normalizedKey,         // 规范化键（消歧用）
    List<String> aliases          // 别名
) {}

public record Relation(
    String id,
    String sourceEntityId,
    String targetEntityId,
    String type,                  // 关系类型（组成/主治/相关...）
    String source,                // 出自哪个文档/块
    double confidence             // 置信度
) {}
```

### 3.5 枚举（knowly-common）

```java
public enum ParseStatus { SUCCESS, PARTIAL, FAILED }

public enum BlockType {
    HEADING("标题"), PARAGRAPH("段落"), LIST("列表"),

    // 带描述字段，便于日志和 UI 展示

    BlockType(String desc) { this.description = desc; }

public enum StageStatus { PENDING, IN_PROGRESS, SUCCESS, FAILED }
```

## 4. SPI 接口清单

> 所有可替换组件定义为 SPI 接口在 knowly-core。第三方可通过 ServiceLoader 或 Spring `@Component` 注册实现。

### 4.1 摄取层接口

```java
public interface DocumentParser {
    /** 该解析器是否支持此文件 */
    boolean supports(String fileName, String mimeType);
    /** 解析文件为 RawDocument */
    RawDocument parse(Path filePath) throws ParseException;
    /** 解析器优先级（多解析器都能处理时，取优先级高的） */
    default int priority() { return 0; }
}

public interface LayoutAnalyzer {
    /** 版面分析：识别双栏/表格/页眉页脚/标题区域，返回带版面信息的文本 */
    AnalyzedLayout analyze(Path filePath, String rawText) throws LayoutException;
}

public interface OcrEngine {
    boolean supports(String imageFormat);
    String ocr(Path imagePath, List<String> languages) throws OcrException;
}

public interface AsrEngine {  // v0.2，v0.1 仅预留接口
    String transcribe(Path mediaPath) throws AsrException;
}
```

**实现**：
- `TikaDocumentParser`：PDF/DOC/DOCX/PPT/XLS/HTML/TXT（Tika 兜底）
- `PdfDocumentParser`：PDF 专用，先文本提取，失败转 OCR
- `RuleBasedLayoutAnalyzer`：轻量版面分析（基于 PDFBox 文本块坐标 + 规则）
- `TesseractOcrEngine`：Tesseract OCR

### 4.2 清洗层接口

```java
public interface TextCleaner {
    /** 清洗单个文档的文本（编码修复、去噪、繁简统一） */
    String clean(String rawText, RawDocument source);
}

public interface DedupStrategy {
    DedupResult check(RawDocument doc);        // 文件级
    DedupResult checkChunk(TextChunk chunk);   // 段落级
}

public interface ChunkingStrategy {
    /** 把文档切成块 */
    List<TextChunk> chunk(RawDocument doc);
}
```

**实现**：
- `DefaultTextCleaner`：编码修复 + 去噪 + 繁简统一（责任链串联多个 cleaner）
- `HashDedupStrategy`：内容哈希去重（精确，文件级）
- `MinHashDedupStrategy`：MinHash + LSH 相似度去重（近似，段落级，标记不删）
- `StructureAwareChunking`：两阶段分段（默认）——阶段一 PreChunker 按结构边界切，阶段二按 max_size 切
- `SemanticChunking`：语义分段（可选）——用 embedding 余弦相似度切
- `FixedSizeChunking`：按字数切（备用）

### 4.3 向量化层接口

```java
public interface EmbeddingProvider {
    float[] embed(String text);
    List<float[]> embedBatch(List<String> texts);   // 批量（推荐，省 API 调用）
    int dimension();                                 // 向量维度（MVP 固定 1024）
}
```

**实现**：`DashScopeEmbeddingProvider`（基于 Spring AI 的 DashScope starter）

### 4.4 产出层接口（ChunkSink）— 核心抽象

```java
public interface ChunkSink extends AutoCloseable {
    String type();                                   // "markdown" / "jsonl" / "pgvector" / "qdrant" ...
    boolean requiresEmbedding();                     // 是否需要 embedding（向量库 true，Markdown/JSONL false）
    void write(List<TextChunk> chunks);              // 写入清洗阶段产物（所有 sink 都实现）
    default void writeEmbedded(List<EmbeddedChunk> chunks) {}  // 写入向量化后产物（仅 requiresEmbedding 的 sink）
    void deleteByDocument(String documentId);        // 删除某文档的所有产物（增量更新清理 + 跨sink补偿）
    @Override void close();
}
```

**Sink 实现矩阵**：

| Sink | type() | requiresEmbedding | 版本 |
|---|---|---|---|
| MarkdownSink | `markdown` | false | v0.1 |
| JsonlSink | `jsonl` | false | v0.1 |
| QdrantSink | `qdrant` | true | v0.1（默认推荐） |
| PgVectorSink | `pgvector` | true | v0.1 |

### 4.7 状态存储与任务仓储接口

> 分两层：StateRepository 管断点续跑（job_files 表），JobRepository 管清洗任务/历史（clean_jobs 表）。

```java
// 断点续跑状态（job_files 表）
public interface StateRepository {
    void markStage(String jobId, String filePath, String contentHash, String documentId, ProcessStage stage, StageStatus status);
    StageStatus getStageStatus(String jobId, String filePath, ProcessStage stage);
    ProcessStage getLastCompletedStage(String jobId, String filePath);
    /** 检测某个 job 是否有未完成的文件（启动时判断是否需要提示续跑） */
    boolean hasUnfinishedFiles(String jobId);
    /** 清理某 job 的所有状态（用户取消时） */
    void cleanByJob(String jobId);
}

// 清洗任务（clean_jobs 表，只存当前运行任务，不累积历史）
public interface JobRepository {
    CleanJob create(CleanJob job);                    // 创建清洗任务（新任务启动时可清理旧的已完成记录）
    void updateStatus(String jobId, JobStatus status); // 更新状态
    void finish(String jobId, JobResult result);       // 完成（成功/失败），写统计和产出位置
    Optional<CleanJob> findCurrent();                  // 当前任务（RUNNING 或最近一次未完成的）
    Optional<CleanJob> findUnfinished();               // 检测是否有未完成任务（启动时提示续跑）
    void cleanFinished();                              // 清理已完成的任务记录（新任务启动时调）
}
```

**实现**：均用 SQLite（`SqliteStateRepository` / `SqliteJobRepository`）。

## 6. 核心算法实现

### 6.1 两阶段分段（StructureAwareChunking）— v0.1 默认

**阶段一：PreChunker（按结构边界切 pre-chunk）**

```
输入：RawDocument.content（含版面分析的结构标记）
处理：
  1. 解析结构标记（标题行：以"第X章""X、"、字体大小、缩进、空行识别）
  2. 构建"结构树"：文档 → 章 → 节 → 段落
  3. 遍历元素流，遇到结构边界（新标题/新章节/版面区域变化）就切一刀
  4. 只管"在哪切"，不管切出来的多大
输出：List<PreChunk>（可能很大或很小）
```

**阶段二：按 max_size 切最终 chunk**

```
输入：List<PreChunk>
处理：
  1. 若 pre-chunk ≤ max_size（如 500 字），作为一个 chunk
  2. 若 pre-chunk > max_size，按句号/换行二次切分（_TextSplitter 按分隔符优先级从右往左切，不切单词）
  3. 相邻小 pre-chunk 可合并（直到接近 max_size）
  4. 保留 overlap（如 50 字），相邻 chunk 共享重叠内容
  5. 每个 chunk 带上所属章节标题（metadata.sectionTitle）
输出：List<TextChunk>
```

**替换策略**：不同分段策略只差阶段一的边界规则。basic 传空边界，by_title 传 `[isTitle]`，semantic 传 `[embeddingSimilarityDrop]`。

### 6.2 Semantic 分段（SemanticChunking）— v0.1 可选

```
输入：RawDocument
处理：
  1. 先按句子/小段切分文本（粗切）
  2. 对每个小段算 embedding
  3. 计算相邻小段的 embedding 余弦相似度
  4. 相似度低于阈值（默认 0.7，可配）处切一刀——语义边界
  5. 相邻语义块合并到接近 max_size
输出：List<TextChunk>
注意：此策略消耗 embedding API，默认不启用，用户显式配置 strategy: semantic 才开
```

### 6.3 轻量版面分析（RuleBasedLayoutAnalyzer）

```
输入：PDF 文件 + 原始文本
处理：
  1. 用 PDFBox 提取文本块的坐标（x, y, width, height）+ 字体大小
  2. 双栏检测：统计文本块 x 坐标分布，若呈双峰（左右两簇），按列分别提取，
     按"左列从上到下 → 右列从上到下"拼接
  3. 页眉页脚检测：每页顶部/底部固定 y 区域内、跨页重复出现的短文本 → 标记 Header/Footer，
     去噪阶段移除
  4. 标题层级：按字体大小 + 加粗聚类，最大字号 → H1，次大 → H2 ...
  5. 表格检测（简化）：检测密集网格线或对齐的文本块 → 标记 TABLE
  6. 版面 bbox 与 PDF 原生文本 token 取交集（不靠 OCR 重转录，省时且准）
输出：AnalyzedLayout（带版面区域信息的文本）
```

### 6.4 两级去重

**文件级（精确）**：
```
对每个 RawDocument 计算 contentHash（TextNormalizer.normalize 后的 SHA-256）
哈希相同 → 完全重复，保留首个，其余标记 DUPLICATE_OF:xxx
```

**段落级（近似）**：
```
对每个 TextChunk 算 MinHash 签名（stream-lib）
LSH 把签名分桶，相同桶内的 chunk 做精确相似度比较（Jaccard）
Jaccard > 阈值（默认 0.85）→ 近似重复，标记但不删除（保留对照版本）
```

### 6.5 扫描版 PDF 检测

```
解析 PDF 后：
  if (提取的字符数 / 页数 < 10)  →  判定扫描版
  →  PDF 转图片 → 调 OCR → 重新得到文本
```

## 7. 数据库设计

> 知了有两类存储：**SQLite（必装，核心业务存储）** 和 **向量库（可选，Qdrant 或 PgVector 二选一）**。
> SQLite 存 admin 账号、当前任务状态、断点续跑状态、配置；向量库只在用户配置了向量 sink 时才需要。

### 7.1 SQLite 核心表（必装，文件型零运维）

数据库文件：`.knowly/knowly.db`

#### users 表（admin 账号，v0.1 仅一条记录，预留多用户）

```sql
CREATE TABLE IF NOT EXISTS users (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    username      TEXT    NOT NULL UNIQUE,
    password_hash TEXT    NOT NULL,              -- bcrypt 哈希
    role          TEXT    NOT NULL DEFAULT 'ADMIN',  -- ADMIN/USER（v0.1 只有 ADMIN）
    created_at    TEXT    NOT NULL DEFAULT (datetime('now'))
);
```

#### clean_jobs 表（当前运行任务状态，不累积历史）

> **只存当前运行的任务**，用于任务调度和断点续跑。完成后状态保留（供断点续跑检测），但**不作为历史列表查询**——知了是工具不做历史归档。新任务启动时可清理旧的已完成记录。

```sql
CREATE TABLE IF NOT EXISTS clean_jobs (
    id              TEXT    PRIMARY KEY,          -- UUID
    user_id         INTEGER NOT NULL,             -- 发起者（v0.1 恒为 admin 的 id）
    source_path     TEXT    NOT NULL,             -- 清洗的源文件/目录路径
    config_snapshot TEXT    NOT NULL,             -- 清洗配置的 JSON 快照（断点续跑复现用）
    status          TEXT    NOT NULL,             -- PENDING/RUNNING/SUCCESS/FAILED/CANCELED
    started_at      TEXT,
    finished_at     TEXT,
    output_location TEXT,                         -- 产出位置（完成时填，供前端展示）
    stats           TEXT,                         -- 统计 JSON：{total_files, succeeded, failed, total_chunks}
    error_summary   TEXT,                         -- 失败摘要（FAILED 时）
    created_at      TEXT    NOT NULL DEFAULT (datetime('now')),
    FOREIGN KEY (user_id) REFERENCES users(id)
);
CREATE INDEX IF NOT EXISTS idx_jobs_status ON clean_jobs(status);
```

> **配置模板不在此表**——配置模板是本地 YAML 文件（`$KNOWLY_HOME/templates/*.yaml`），不进数据库。见 7.2 节。

#### job_files 表（断点续跑状态，按 job 隔离）

```sql
CREATE TABLE IF NOT EXISTS job_files (
    job_id          TEXT    NOT NULL,
    file_path       TEXT    NOT NULL,
    content_hash    TEXT,
    document_id     TEXT,
    stage           TEXT    NOT NULL,             -- INGEST/CLEAN/EMBED/SINK
    status          TEXT    NOT NULL,             -- PENDING/IN_PROGRESS/SUCCESS/FAILED
    updated_at      TEXT,
    PRIMARY KEY (job_id, file_path, stage),
    FOREIGN KEY (job_id) REFERENCES clean_jobs(id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_jobfiles_job ON job_files(job_id);
```

#### app_config 表（全局配置：API key 等）

```sql
CREATE TABLE IF NOT EXISTS app_config (
    key             TEXT PRIMARY KEY,             -- 如 dashscope_api_key / default_ocr_languages
    value           TEXT,                         -- 值（敏感信息加密存储，读取时解密+脱敏）
    updated_at      TEXT NOT NULL DEFAULT (datetime('now'))
);
```

### 7.2 配置模板（本地 YAML 文件，不进数据库）

> 用户调好的清洗参数保存为模板，下次复用。**模板是 YAML 文件，不进数据库**——因为配置本来就是文件，且 CLI 也能直接用这些模板，Web 和 CLI 无缝打通。

**目录结构**（`$KNOWLY_HOME/templates/`，默认 `./knowly-workspace/templates/`）：
```
$KNOWLY_HOME/templates/
├── clean-only.yaml              # 内置：纯文件产出（Markdown+JSONL）
├── rag-qdrant.yaml              # 内置：向量化到 Qdrant
├── rag-pgvector.yaml            # 内置：向量化到 PgVector
└── 中医方剂-structure-aware.yaml # 用户自定义模板
```

**文件内容**：就是 pipeline.yaml 的 stages + sinks 部分（不含 input/output，这两个每次清洗时指定）。

**操作**（对应 REST API `/api/templates`）：
- 列出：扫描 `$KNOWLY_HOME/templates/*.yaml`，区分内置（随软件分发）和自定义
- 加载：读文件内容返回 YAML
- 保存：写 YAML 文件（自定义模板）
- 删除：删文件（仅自定义，内置不可删）

### 7.3 向量库表（可选，Qdrant 或 PgVector 二选一）

#### 方案 A：Qdrant（默认推荐）

Qdrant 无需建表，通过 API 创建 collection：
```java
// 创建 collection，维度 1024（text-embedding-v3）
qdrantClient.createCollectionAsync("knowly_chunks",
    VectorParams.newBuilder().setSize(1024).setDistance(Distance.Cosine).build()).get();
```
chunk 写入时带 payload（metadata：document_id/section_title/start_page 等），支持过滤检索。

#### 方案 B：PgVector（可选替代）

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE IF NOT EXISTS knowledge_chunks (
    id            VARCHAR(128)  PRIMARY KEY,          -- chunk id = documentId#ordinal
    document_id   VARCHAR(64)   NOT NULL,
    text          TEXT          NOT NULL,
    embedding     vector(1024),                       -- 固定 1024 维（text-embedding-v3）
    section_title VARCHAR(512),
    section_level SMALLINT,
    start_page    INT,
    source_path   TEXT,
    created_at    TIMESTAMPTZ   DEFAULT NOW(),
    metadata      JSONB         DEFAULT '{}'::jsonb
);

CREATE INDEX IF NOT EXISTS idx_chunks_embedding
    ON knowledge_chunks USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
CREATE INDEX IF NOT EXISTS idx_chunks_document_id ON knowledge_chunks(document_id);
CREATE INDEX IF NOT EXISTS idx_chunks_metadata ON knowledge_chunks USING gin (metadata jsonb_path_ops);
```

> ⚠️ 维度锁定：`vector(1024)` 与 `text-embedding-v3` 绑定。换模型需同步改维度并重算。
> PgVector 的 DDL 执行用受限权限账号（非 superuser）。

> **ChunkSink SPI 统一**：QdrantSink 和 PgVectorSink 都实现 ChunkSink 接口，上层无感。用户配置里选哪个 sink，就写哪个向量库。

### 8.2 pipeline.yaml 完整结构

```yaml
pipeline:
  name: "国学知识库"
  input: ./data/raw                   # 可被命令行 --input 覆盖
  output: ./data/kb                   # 可被命令行 --output 覆盖

  state:
    store: sqlite
    path: ./data/kb/.knowly/knowly.db

  stages:
    ingest:
      parsers: [pdf, doc, docx, image, generic]
      layout_analysis: light          # 轻量版面分析（v0.1）
      ocr:
        enabled: true
        languages: [chi_sim, eng]
        min_chars_per_page: 10        # 扫描版判定阈值

    clean:
      encoding: auto
      normalize:
        fullwidth_to_halfwidth: true
        traditional_to_simplified: true   # 中文默认开
        trim_whitespace: true
      dedup:
        file_level:
          enabled: true
          method: hash
        paragraph_level:
          enabled: true
          method: minhash
          threshold: 0.85
      chunking:
        strategy: structure_aware     # 两阶段分段（默认）
        # strategy: semantic          # 可选：语义分段（消耗 embedding，默认不开）
        max_size: 500
        overlap: 50
        min_size: 50

    embed:                            # 仅当配置了 requiresEmbedding 的 sink 时启用
      provider: dashscope
      model: text-embedding-v3        # 固化：默认 embedding 模型
      dimensions: 1024                # 固化：影响向量库建表 DDL
      api_key: ${DASHSCOPE_API_KEY}
      batch_size: 25
      qps_limit: 10

  # 产出目标（数组，可多选）。不配则默认 markdown + jsonl
  sinks:
    - type: markdown
      dir: ./data/kb/00-clean
      include_chunk_markers: true     # 嵌入 chunk 元数据 HTML 注释
      keep_source_tree: true          # 按原文档目录结构组织

    - type: jsonl
      path: ./data/kb/01-chunks/chunks.jsonl

    - type: pgvector                  # 取消注释即启用
      enabled: false
      host: localhost
      port: 5432
      database: knowly_kb
      user: ${PG_USER}
      password: ${PG_PASSWORD}
      table: knowledge_chunks

    # - type: qdrant                  # v0.2
    #   url: http://localhost:6333
    #   collection: knowly_kb

  error_handling:
    on_file_failure: SKIP_AND_LOG     # 不中断
    retry:
      embedding: { max: 3, backoff: exponential, jitter: true }
```

### 8.3 配置校验规则

启动时校验：
- 必填项缺失（如 pipeline.name）
- 依赖关系（配了 pgvector sink 但没配 embed → 报错；开了 ocr 但没配 languages → 报错）
- 类型/范围（max_size 必须 > 0；qps_limit 必须 > 0）
- 报错格式：明确指出"哪个字段、期望什么、实际什么、怎么改"

## 10. 关键流程时序

### 10.1 端到端流水线（一次 run）

```
CLI/API 启动
  → PipelineEngine 加载配置、校验、实例化各 Stage 和 Sink（工厂+注册表）
  → 扫描 input 目录 → List<文件>
  → 对每个文件（流式，per document）：
      → 查 StateRepository：已处理且哈希不变 → 跳过
      → Ingest：Parser 解析 → 版面分析 → RawDocument
      → 发布 FileStarted 事件
      → Clean：TextCleaner 责任链 → DedupStrategy 去重 → ChunkingStrategy 分段 → TextChunk[]
      → 发布 StageProgress 事件
      → 若有 requiresEmbedding 的 sink：
          → Embed：EmbeddingProvider 批量调 API（RateLimiter 限流 + RetryTemplate 重试）→ EmbeddedChunk[]
      → Sinks 并行写入（MarkdownSink/JsonlSink/PgVectorSink）
      → StateRepository 标记该文件各阶段 SUCCESS
      → 发布 FileCompleted 事件
  → 所有文件完成 → 产出 processing-report.json + error-report.json
  → 发布 PipelineFinished 事件
```

### 10.2 断点续跑

```
用户打开 Web UI → GET /api/jobs/unfinished 检测
  → 有未完成任务 → 前端提示"上次清洗未完成，是否继续/取消"
  → 用户选"继续"（POST /api/jobs/{id}/resume）：
      → 对每个文件查 StateRepository.getLastCompletedStage(jobId, filePath)
      → 全部 SUCCESS → 跳过
      → 某阶段非 SUCCESS → 从该阶段重新开始
      → embed/sink 阶段重跑时，依赖 sink 幂等（按 chunk id 覆盖写）保证无重复
  → 用户选"取消"：清理该任务的 job_files 状态
```

### 10.3 增量更新

```
扫描 source_path 目录 → 对每个文件：
  → 计算 contentHash
  → 对比 job_files 表：哈希相同 → 跳过（已处理且未变）
  → 哈希变化或新增 → 处理：
      → sink.deleteByDocument(documentId)  清理旧数据（documentId 由 hash 派生，路径变也能识别）
      → 重新走 Ingest→Clean→Embed→Sink
```

### 10.4 Web 任务调度（knowly-api）

```
前端 POST /api/jobs（传 source_path + 配置）
  → knowly-api 创建 clean_job 记录（状态 PENDING，存 SQLite）
  → @Async 异步执行 PipelineEngine
  → job 状态 RUNNING
  → PipelineEngine 注册 PipelineEventListener → 转 SSE 推给前端（GET /api/jobs/{id}/events）
  → 执行中：前端通过 SSE 实时收进度
  → 用户可 POST /api/jobs/{id}/cancel → 触发优雅停机
  → 完成：job 状态 SUCCESS/FAILED，写统计和产出位置
```

### 10.5 优雅停机

```
收到 SIGTERM（CLI）或 cancel（API）：
  → 停止接收新文档
  → 等待进行中的文档完成（上限 30s 超时强杀）
  → flush 所有 sink（close）
  → StateRepository 标记进行中文件状态
  → 退出
```

### 10.6 并发互斥（同一时间只允许一个清洗任务）

> 知了是单机工具，clean_jobs 只存当前任务。必须防止 Web 和 CLI 同时启动两个清洗任务，否则状态混乱。

```
启动清洗任务前：
  → 检查 clean_jobs 是否有 RUNNING 状态的任务
  → 有 → 拒绝启动，报错"已有清洗任务在运行中，请先完成或取消"
  → 无 → 创建新任务，状态 RUNNING
```

CLI 和 Web 共用同一个 SQLite，互斥检查通过数据库实现。CANCELED 状态的任务视为已结束，不阻塞新任务。

## 11. CLI 命令设计（knowly-cli）

> CLI 是主入口，负责批处理、自动化、脚本编排。以下命令对应需求 F6.1-F6.5。

### 11.1 run（运行完整流水线）

```bash
knowly run --config pipeline.yaml --input ./docs --output ./kb
```
- 读 YAML 配置 → 扫描 input → 走完整流水线（ingest→clean→[embed]→sinks）→ 产出到 output
- `--config` 可用模板名：`knowly run --template rag-qdrant --input ./docs --output ./kb`（从 `$KNOWLY_HOME/templates/rag-qdrant.yaml` 加载）
- 中断后重跑同命令，自动从断点续跑（检测 job_files 状态）

### 11.2 单阶段运行（F6.2）

```bash
knowly ingest --input ./docs --output ./raw      # 只摄取，产出 RawDocument 序列化
knowly clean --input ./raw --output ./chunks      # 只清洗分段，产出 TextChunk
knowly embed  --input ./chunks --output ./vectors  # 只向量化，产出 EmbeddedChunk
```
- 用途：调试单个阶段、或流水线拆步执行
- 实现：PipelineEngine 支持只跑指定阶段（跳过其他），通过 `--stage` 参数控制

### 11.3 report（查看报告）

```bash
knowly report ./kb    # 显示 processing-report.json + error-report.json 摘要
```

### 11.4 init（初始化配置，F6.4）

```bash
knowly init                    # 在当前目录生成 pipeline.yaml（默认模板）
knowly init --template rag-qdrant  # 用指定模板生成
```
- **init 与配置模板的关系**：`init` 把模板文件**复制到当前目录**作为 pipeline.yaml（运行配置）；模板本身仍在 `$KNOWLY_HOME/templates/`。用户在 pipeline.yaml 上改参数后运行，不影响原模板。
- 区别：模板是"可复用的配置预设"，pipeline.yaml 是"本次运行的实际配置"。

### 11.5 reembed（回灌，F6.5）

```bash
knowly reembed --input ./kb/00-clean --sink qdrant --collection my_kb
```
- **用途**：从已产出的 Markdown 文件重建向量库（换 embedding 模型、或之前只产了文件现在想落向量库）
- **流程**：
  1. 扫描 `--input` 目录下的 `.md` 文件
  2. 解析每个 `.md` 里的 HTML 注释 chunk 标记（`<!-- knowly:chunk id="..." -->`），还原 TextChunk
  3. 对每个 TextChunk 调 EmbeddingProvider 生成向量 → EmbeddedChunk
  4. 写入指定 sink（qdrant/pgvector），按 chunk id 幂等 upsert
- **不重新清洗**：直接用已清洗的 chunk，只补 embedding 步骤

## 12. 配置与安全补充

### 12.1 两套配置的关系与合并

知了有两类配置，**职责不同，运行时合并**：

| 配置来源 | 存哪 | 存什么 | 谁改 |
|---|---|---|---|
| **全局设置**（app_config 表） | SQLite | API Key、默认 OCR 语言、默认分段策略、文件大小上限 | Web 设置页 / CLI `knowly config` |
| **清洗配置**（pipeline.yaml） | YAML 文件 | stages 参数、sinks 选择、input/output 路径 | Web 工作台 / 手编 YAML |

**合并规则**（运行时）：
1. 加载 knowly-defaults.yaml（内置默认）
2. 覆盖加载 pipeline.yaml（本次清洗配置）
3. **环境变量 `${VAR}` 解析优先级**：pipeline.yaml 里的 `${DASHSCOPE_API_KEY}` 先查环境变量，没有则查 app_config 表（Web 设置页配的值）
4. 这样 CLI 用户用环境变量，Web 用户用设置页，两者都能工作

### 12.2 API Key 加密方案

app_config 表里的敏感值（如 `dashscope_api_key`）**加密存储**：
- **加密算法**：AES-256-GCM
- **密钥来源**：首次启动时生成一个主密钥，存到 `$KNOWLY_HOME/.master-key` 文件（文件权限 600，仅当前用户可读）
- **读写**：写入时加密，读取时解密；返回给前端时额外脱敏（只显示 `sk-xxxx...xxxx`）
- **密钥不进代码、不进日志、不进 Git**

> [待定] v0.1 是否需要这么严格？如果只本机单用户，明文存 SQLite 文件权限 600 也可接受。加密方案为生产级预留，v0.1 可简化为文件权限保护 + 脱敏显示。

### 12.3 配置模板路径统一

> 之前模板在用户主目录，产出在工作目录，数据分散。统一到**一个工作目录**下（`$KNOWLY_HOME`）。

**统一方案**：知了的所有数据（配置模板、产出、SQLite、日志）都在一个工作目录下，默认 `./knowly-workspace/`，可通过 `KNOWLY_HOME` 环境变量覆盖。

```
./knowly-workspace/             # KNOWLY_HOME（默认当前目录下）
├── templates/                  # 配置模板（YAML）
├── data/
│   ├── knowly.db               # SQLite（admin/任务/断点/设置）
│   └── kb/                     # 清洗产出（Markdown/JSONL/reports）
└── logs/                       # 日志
```

这样备份/迁移只管一个目录。CLI 和 Web 共用同一个 `KNOWLY_HOME`。
