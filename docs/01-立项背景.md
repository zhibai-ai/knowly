## 一、它是什么

**知了（knowly）是一个开源的数据 AI 化清洗工具**：把任意一批原始文档（PDF / Word / 图片 / 视频等），自动转换成 AI 可用的结构化知识（干净文本 + 向量 + 知识图谱）。

一句话定位：

> **Turn raw documents into AI-ready knowledge. —— 把原始文档变成 AI 可用的知识。**

名字由来：蝉饮露高鸣，古人喻为清通透；"知了"即"知晓了悟"。沉睡在文件里的资料，经知了处理后，便能为 AI 所"知晓"。

---

## 二、为什么需要它

### 痛点：从"有资料"到"AI 能用"，中间隔着一座山

当下任何 RAG（检索增强生成）系统、AI 知识库、Agent 应用，都面临同一个最朴素却最耗时的难题：

> **手头有一堆 PDF、Word、扫描件、教学视频，要让 AI 能基于这些内容回答问题，中间的"数据准备"工作极其繁琐。**

这个"中间过程"至少包含：

1. **格式解析**：PDF / DOC / DOCX / PPT / 图片，格式各异，逐个提取文本
2. **编码与乱码**：老文件 GBK 编码、文件名乱码、特殊字符
3. **去重**：同一内容多版本并存（不同人整理的笔记），不能简单堆叠
4. **分段**：文本要切成适合检索的"块"，但怎么切大有学问
5. **向量化**：每段文本要转成 embedding，存入向量库
6. **（进阶）图谱化**：从文本里抽取实体和关系，构建知识图谱，支撑 GraphRAG

**这套流程在几乎所有 AI 知识库项目里都要重写一遍。** 它本身没有业务价值，却是绕不开的地基工程。每个团队都在重复造轮子，且各自做得粗糙。

### 现状：现有工具要么太窄，要么太重

| 现有方案 | 问题 |
|---|---|
| LangChain / LlamaIndex 的文档加载器 | 只解决"加载"，清洗/去重/分段策略薄弱，需大量手工拼装 |
| LlamaIndex 的 ingestion pipeline | 偏 Python，Java 生态缺位；流程定制不够灵活 |
| 各向量库自带的导入工具 | 只管"导入自己的库"，不管清洗质量，不跨库 |
| Microsoft GraphRAG | 只做图谱构建那一段，不管前面的清洗，且 Python only |
| 商业 ETL 工具（Airbyte 等） | 偏数据同步，不为 AI 知识库场景设计 |

**缺口**：缺少一个"专为 AI 知识库场景设计、多格式解析到向量化/图谱化一条龙、Java 生态、可配置可扩展、可开源"的工具。知了要填这个缺口。

## 三、它从哪来（起源）

知了最初脱胎于「守一 onesway」国学顾问系统的需求：

> 守一系统需要把倪海厦老师的天纪（命理）+ 人纪（中医）教学资料——包含数百个 PDF、数千份 Word 笔记、数百个教学视频、上千张图片——清洗成可被 AI 检索的知识库。

在守一项目里，我们用 Python 做了一次针灸学科的清洗验证（提取出 145 万字干净文本，验证了 RAG 检索可行）。但过程中深刻体会到：**这套清洗流程应该被产品化、通用化、Java 化**，而不是每次在每个项目里重写。

于是知了被独立出来，成为一个**与守一解耦、面向所有 AI 知识库场景的通用开源工具**。守一是它的第一个使用者，但绝不是唯一。

---

## 四、它解决什么（价值主张）

| 对谁 | 价值 |
|---|---|
| **RAG 系统开发者** | 一条命令把文档库变成向量库，省去数周的数据准备 |
| **企业 AI 应用团队** | 统一的知识入库流程，可审计、可复现、可扩展 |
| **研究者** | 可配置的清洗策略，便于实验不同分段/向量化方案对检索效果的影响 |
| **任意"文档→知识"场景** | 法律、医疗、教育、企业文档，凡是要让 AI 基于自有资料回答的，都能用 |

---

## 五、它的边界（不做什么）

明确边界，避免项目膨胀：

- **不做知识库的"查询服务"**——知了只负责"造库"，不负责"查库"。查询是消费方（如守一）的事。
- **双入口：CLI 为主 + Web 为调优工作台**——CLI 做批处理/自动化，Web 做清洗调优（看进度/预览分段/检查产出），两者共享 knowly-core，配置 YAML 桥接。**Web 不是管理平台**，不做知识库/文档/历史等平台功能。
- **不绑定单一 AI 厂商**——LLM、embedding、向量库都要可插拔。
- **不绑定单一领域**——不能只认中医/命理，必须对任意文档通用。
- **不做实时流式摄入**——MVP 是批处理（处理一批文件产出知识库），不是增量流式。

## 六、产出形态：多 Sink（重要）

知了的产出**不绑定向量库**。清洗后的知识可以"落库"，也可以不落库——由使用方按需选择。这是知了区别于同类工具的关键设计。

| 产出形态（Sink） | 产物 | 用途 | 版本 |
|---|---|---|---|
| **Markdown**（默认） | 按章节组织的 `.md` 文件 | 通用文本资产；直接喂 LLM；Git 可 diff、可审计；零运维 | v0.1 |
| JSONL | 每行一个 chunk 的结构化文件 | 程序化消费、导入其他系统 | v0.1 |
| PgVector | 向量 + 文本 + 元数据 | RAG 检索（默认向量库） | v0.1 |
| Qdrant / Milvus | 向量 + 文本 + 元数据 | RAG 检索（可选向量库） | v0.2 |
| Elasticsearch | BM25 文本检索 | 混合检索 | v0.3 |

**关键设计**：不配任何向量库时，知了默认产出 Markdown + JSONL。**这意味着 `git clone` 后无需安装任何数据库即可看到产物**，是知了作为开源工具的"aha moment"。详见系统架构"Sink 抽象"章节。

## 七、成功标准

知了的 MVP 算成功，需要满足：

1. **能跑通**：用守一的天纪资料（PDF + Word）跑一遍，产出可被 RAG 检索的向量库，且问答效果经过验证
2. **能复用**：换一批完全不同的文档（如一份英文论文集），改改配置就能跑，不改代码
3. **能扩展**：想换向量库（PgVector→Qdrant）、想加新格式解析，通过插件/SPI 实现，不动核心
4. **能开源**：文档清晰、有示例、Apache 2.0 协议，别人能看懂并用起来
5. **零运维可试用**：不配数据库也能产出 Markdown，5 秒内感知价值

## 八、与守一 onesway 的关系

```
┌─────────────────┐   产出知识库（向量+图谱+Markdown）   ┌─────────────────┐
│   知了 knowly    │ ─────────────────────────────→ │  守一 onesway    │
│  （造库工具）    │                                 │ （消费方/应用）   │
│  独立开源项目    │                                 │  独立项目        │
└─────────────────┘                                 └─────────────────┘
   通用、可复用                                      守一只是知了的
   不耦合守一                                        一个使用者
```

- 知了**不依赖**守一的任何代码
- 守一**依赖**知了产出的知识库（标准格式），但不依赖知了的实现
- 两者可独立演进、独立开源、独立发版

## 九、竞品调研与差异化定位

立项前调研了市面同类产品，结论：**没有一个竞品同时满足"Java + 一条龙 + 纯造库 + 多 Sink + 中文优化"这五点。**

### 直接竞品

| 项目 | 语言/协议 | 定位 | 知了的差异化 |
|---|---|---|---|
| [Unstructured.io](https://github.com/Unstructured-IO/unstructured) | Python / Apache 2.0 | "ETL for LLMs"，64+ 格式解析 | **Java 生态唯一选手**；纯造库不绑 SaaS；默认 Markdown 产出 |
| [RAGFlow](https://ragflow.io) | Python / Apache 2.0 | 深度文档理解（DeepDoc）+ RAG 一体化 | 知了**专注造库不做查询**；学习其 DeepDoc 版面分析思路（v0.1 引入轻量版面分析） |
| [Dify Knowledge Pipeline](https://dify.ai) | Python / 开源 | Agent + RAG 平台 | 知了是独立工具，不是平台的一个子功能 |
| [Docling (IBM)](https://github.com/DS4SD/docling) | Python / MIT | PDF 解析 + chunking | 知了是**全流程**（解析→清洗→分段→向量化→图谱），Docling 只做解析 |
| LlamaIndex Ingestion Pipeline | Python | 框架内置摄取流水线 | 知了是**独立可运行工具**，非框架的一部分 |

### 差异化五要素

```
        Python only          ← 知了：Java 生态唯一选手（Tika 同栈优势）
            │
            ▼
    只做一段(解析/图谱)       ← 知了：解析→清洗→分段→向量化→(图谱) 一条龙
            │
            ▼
   强绑定查询/RAG 引擎        ← 知了：纯造库，不碰查询，与消费方解耦
            │
            ▼
    落库强耦合(必须连向量库)   ← 知了：多 Sink 抽象，Markdown 为默认
            │
            ▼
      无/弱中文优化            ← 知了：繁简统一、中文分段、中文实体消歧为默认
```

### 必须向竞品学习

1. **学 RAGFlow DeepDoc**：v0.1 就引入轻量版面分析（双栏/表格/页眉页脚识别），提升 PDF 清洗质量
2. **学 Unstructured 的 chunking 可插拔**：v0.1 先做 structure-aware 分段，SPI 预留 semantic chunking（v0.2）
3. **学 Dify/RAGFlow 的可观测性**：流水线每步可见（进度/耗时/样本预览），这是 Web 调优工作台的核心价值——但只借鉴可视化交互，不借鉴其平台管理模式

## 十、技术栈定调

- **核心语言：Java 17+ / Spring Boot 3.x**
  - 理由：守一同栈；Apache Tika / POI 是 Java 文档解析事实标准；企业级
- **Python 后路（预留）**：AI/LLM 生态 Python 更成熟（Spring AI 2024 才起来）。v0.1 纯 Java 实现；**未来若图谱抽取、semantic chunking 等 LLM 密集功能的 Python 生态优势明显，可通过子进程 / gRPC 调用 Python 模块**。v0.1 不实现，仅在系统架构埋伏笔。
- **前端**：v0.2 用 React + Vite（独立工程 `knowly-web`）
